# Claude Code Haha

<p align="right"><strong>中文</strong> | <a href="./README.en.md">English</a></p>

基于 Claude Code 泄露源码修复的**本地可运行版本**，支持接入任意 Anthropic 兼容 API（如 MiniMax、OpenRouter 等）。

> 原始泄露源码无法直接运行。本仓库修复了启动链路中的多个阻塞问题，使完整的 Ink TUI 交互界面可以在本地工作。

<p align="center">
  <img src="docs/00runtime.png" alt="运行截图" width="800">
</p>

## 功能

- 完整的 Ink TUI 交互界面（与官方 Claude Code 一致）
- `--print` 无头模式（脚本/CI 场景）
- 支持 MCP 服务器、插件、Skills
- 支持自定义 API 端点和模型
- 降级 Recovery CLI 模式
- **高效任务模式 `/et`**：把需求拆成可并行、带依赖、多角色评审的任务树（[用法](#高效任务模式-et)）
- **飞书集成**：确认关口、权限请求、升级通知都可以在飞书卡片上处理

## 快速开始

### 方式 A：下载编译好的二进制（不需要装 Bun）

从 [Releases](https://github.com/bise86/claude-code/releases) 下载对应平台的单文件二进制：

| 平台 | 文件 |
|------|------|
| Linux x64 | `claude-haha-linux-x64` |
| macOS Apple Silicon | `claude-haha-darwin-arm64` |
| macOS Intel | `claude-haha-darwin-x64` |
| Windows x64 | `claude-haha-windows-x64.exe` |

```bash
chmod +x claude-haha-linux-x64
./claude-haha-linux-x64 --version
```

二进制里已经打包了运行时和全部依赖，机器上不需要 Bun 和 node_modules。但**仍然需要配置 API 凭据**——见下面第 3 步，把 `.env` 放在二进制同目录，或直接用环境变量。

### 方式 B：从源码运行

### 1. 安装 Bun

本项目运行依赖 [Bun](https://bun.sh)。如果你的电脑还没有安装 Bun，可以先执行下面任一方式：

```bash
# macOS / Linux（官方安装脚本）
curl -fsSL https://bun.sh/install | bash
```

如果在精简版 Linux 环境里提示 `unzip is required to install bun`，先安装 `unzip`：

```bash
# Ubuntu / Debian
apt update && apt install -y unzip
```

```bash
# macOS（Homebrew）
brew install bun
```

```powershell
# Windows（PowerShell）
powershell -c "irm bun.sh/install.ps1 | iex"
```

安装完成后，重新打开终端并确认：

```bash
bun --version
```

### 2. 安装项目依赖

```bash
bun install
```

### 3. 配置环境变量

复制示例文件并填入你的 API Key：

```bash
cp .env.example .env
```

编辑 `.env`：

```env
# API 认证（二选一）
ANTHROPIC_API_KEY=sk-xxx          # 标准 API Key（x-api-key 头）
ANTHROPIC_AUTH_TOKEN=sk-xxx       # Bearer Token（Authorization 头）

# API 端点（可选，默认 Anthropic 官方）
ANTHROPIC_BASE_URL=https://api.minimaxi.com/anthropic

# 模型配置
ANTHROPIC_MODEL=MiniMax-M2.7-highspeed
ANTHROPIC_DEFAULT_SONNET_MODEL=MiniMax-M2.7-highspeed
ANTHROPIC_DEFAULT_HAIKU_MODEL=MiniMax-M2.7-highspeed
ANTHROPIC_DEFAULT_OPUS_MODEL=MiniMax-M2.7-highspeed

# 超时（毫秒）
API_TIMEOUT_MS=3000000

# 禁用遥测和非必要网络请求
DISABLE_TELEMETRY=1
CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1
```

### 4. 启动

#### macOS / Linux

```bash
# 交互 TUI 模式（完整界面）
./bin/claude-haha

# 无头模式（单次问答）
./bin/claude-haha -p "your prompt here"

# 管道输入
echo "explain this code" | ./bin/claude-haha -p

# 查看所有选项
./bin/claude-haha --help
```

#### Windows

> **前置要求**：必须安装 [Git for Windows](https://git-scm.com/download/win)（提供 Git Bash，项目内部 Shell 执行依赖它）。

Windows 下启动脚本 `bin/claude-haha` 是 bash 脚本，无法在 cmd / PowerShell 中直接运行。请使用以下方式：

**方式一：PowerShell / cmd 直接调用 Bun（推荐）**

```powershell
# 交互 TUI 模式
bun --env-file=.env ./src/entrypoints/cli.tsx

# 无头模式
bun --env-file=.env ./src/entrypoints/cli.tsx -p "your prompt here"

# 降级 Recovery CLI
bun --env-file=.env ./src/localRecoveryCli.ts
```

**方式二：Git Bash 中运行**

```bash
# 在 Git Bash 终端中，与 macOS/Linux 用法一致
./bin/claude-haha
```

> **注意**：部分功能（语音输入、Computer Use、Sandbox 隔离等）在 Windows 上不可用，不影响核心 TUI 交互。

## 高效任务模式 `/et`

把一句需求拆成一棵**可并行、带依赖、多角色评审**的任务树，自动跑完。

```bash
/et 把登录模块重构成 JWT，补上测试
```

它会先弹一个**启动关口**让你确认：目标、并行数、名册（谁在什么环节干活）、预估调用数上限。确认之后自主执行，只在需要工具权限、触发安全阀、或合并冲突时才打扰你。跑完再弹一个**收口关口**，让你选合并 / 推送 / 保留 / 丢弃。

### 两个核心概念：员工与角色

这两个词很容易混，先分清：

| 概念 | 是什么 | 配在哪 |
|------|--------|--------|
| **员工（staff）** | 一个**可派遣的身份**，自带模型、API 地址、工具集 | `settings.json` 的 `roles[]` |
| **角色（role）** | 任务里的一个**职能**，比如「架构师」「安全」 | `settings.json` 的 `efftaskRoles[]`，或直接写在提示词里 |

**多对多**：一个员工可以担任多个角色，一个角色也可以由多个员工担任。

一个角色配了多个员工时，他们**必须收敛成一个产出**——具体怎么收敛，取决于环节（见下）。

### 环节：任务的七个步骤

每个节点先被定为**拆分型**或**执行型**，再按形态走一串环节：

- **拆分型**：分析 → 质疑讨论 →（等全部子任务完成）→ **集成验收** → 观察
- **执行型**：分析 → 质疑讨论 → 执行 → 测试验证 → 验收 → 观察 →（自动合并进集成分支）

> **集成验收不做合并。** 合并早就发生了——每个执行型节点自己通过验收时，就把它的工作区合进了集成分支。集成验收判的是另一件事：**「这些子任务的结果合起来，达成父节点的目标了吗」**。所以它必须等全部子任务完成——少一块就问不了这个问题。它也是唯一能发现「当初拆漏了」的地方：裁决不通过时可以直接提出补救子任务，挂上去跑完再重新验收。
>
> 执行型节点的合并是**机械**的，没有角色关口。所以「集成验收」这个环节只对拆分型节点生效。

**自由的是角色，固定的是环节。** 你可以定义任意多个角色、任意取名、指定任意员工担当、写任意的产出与作用。不自由的只有一件事：这个角色挂在**哪个环节**上。环节是流水线状态机的骨架，它决定这一席什么时候被调用、能不能拿到写工具、`--resume` 之后还在不在。

> 环节列表**会随版本增长**——这一版就从 5 个长到了 7 个。写一个不存在的环节名会被明确拒绝并告诉你合法值，而不是静默丢弃。

### 完整配置示例

`~/.claude/settings.json`（或项目下的 `.claude/settings.json`）：

```jsonc
{
  "roles": [
    // ── 员工：可派遣的身份 ──
    {
      "name": "opus-架构",
      "whenToUse": "架构与拆分合理性评审",
      "execMode": "api",
      "apiProtocol": "anthropic",
      "apiUrl": "https://api.anthropic.com",
      "apiToken": "sk-ant-xxx",
      "model": "claude-opus-4-8"
    },
    {
      "name": "ds-测试",
      "whenToUse": "跑测试、做变异验证",
      "execMode": "api",
      "apiProtocol": "openai",
      "apiUrl": "https://api.deepseek.com/v1",
      "apiToken": "sk-xxx",
      "model": "deepseek-chat",
      // 员工侧也能声明「我能当哪些角色」（双向配置）
      "efftaskRoles": ["测试官"]
    },
    {
      // OpenAI 官方的推理模型：走 Responses 协议才看得到思考过程
      "name": "gpt5-方案",
      "whenToUse": "复杂方案设计",
      "execMode": "api",
      "apiProtocol": "openai-responses",   // → {apiUrl}/responses
      "apiUrl": "https://api.openai.com/v1",
      "apiToken": "sk-proj-xxx",
      "model": "gpt-5.1",
      "thinkingDepth": "xhigh"             // 五档:low/medium/high/xhigh/max
    }
  ],

  "efftaskRoles": [
    // ── 角色：任务里的职能 ──
    {
      "name": "架构师",
      "step": "质疑讨论",
      "output": "通过/阻断裁决 + 每条阻断指向具体的边界问题",
      "purpose": "质疑这份拆分：有没有漏项、子任务间有没有隐藏依赖",
      "staff": ["opus-架构"]
    },
    {
      "name": "测试官",
      "step": "测试验证",
      "output": "实际执行的命令、原始输出、通过/阻断裁决",
      "purpose": "真的把测试跑起来，不读执行者的自述",
      "staff": ["ds-测试"]
    },
    {
      "name": "验收官",
      "step": "验收",
      "output": "验收裁决",
      "purpose": "逐条核对验收点"
      // 不写 staff = 由当前主模型兼任
    }
  ]
}
```

### 角色字段

四个必填字段缺任何一个，该角色**不生效**，并在启动关口上说明原因（不静默丢弃）：

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | 是 | 角色名，任意取 |
| `step` | 是 | 在哪个环节用。见下表。旧键名 `stage` 仍然读得进来 |
| `output` | 是 | 产出什么 |
| `purpose` | 是 | 起什么作用 |
| `staff` | 否 | 由哪些员工担当。**省略 = 主模型兼任** |

`step` 的合法值（中文英文都收，落盘统一成英文）：

| 中文 | 英文 | 多员工时怎么收敛成一个产出 |
|------|------|--------------------------|
| 分析 | `plan` | **两种，可选**：顺序精化（默认）或方案融合圆桌。见下一节 |
| 质疑讨论 | `review` | **圆桌**：各自独立裁决，按通过门槛合成一个结论 |
| 执行 | `execute` | **只能一个员工**（物理约束：工作区路径不含员工维度） |
| 测试验证 | `verify` | 圆桌 |
| 验收 | `accept` | 圆桌 |
| 集成验收 | `integrate` | 圆桌。**只对拆分型节点生效**；没配时回落到验收席位。旧名「集成提交」仍可写 |
| 观察 | `observer` | **各自打分，取最低分**；其余人的理由一条不丢地记在旁边 |

### 分析环节：两种收敛方式

分析是唯一一个可以选收敛方式的环节，因为「多个人一起想方案」有两种截然不同的做法：

| 方式 | 怎么跑 | 什么时候用 |
|------|--------|-----------|
| **顺序精化**（默认） | 第一位起草，后面每一位在**前一稿上**修订。全程只有一份稿子 | 方向已经清楚，想要的是逐层加固 |
| **方案融合圆桌** | 每一位**独立**起草，互相看不到；然后由最后一席把所有稿子融合成一份最优解 | 方向还没定，怕第一稿把后面所有人锚死 |

顺序精化的代价是**锚定效应**：第一稿的框架基本就是最终框架，后面的人在修订而不是重想。融合圆桌拿掉了这个锚，代价是多一次模型调用（融合那次）。

在指令里说一句就能切：

```bash
/et 设计一套限流方案。分析用圆桌
```

融合席位是**最后一席**（名册里排在最后的那个员工），它拿到的是匿名化的「稿 A / 稿 B / 稿 C」——看不到谁写的，避免按人而不是按内容取舍。融合结果作为正式方案往下走，**落选的稿子不丢**：每份的方案正文存进 `node.md` 的「备选方案」段落，事后能查为什么没选它。存的是方案正文那一段（超长会截断并标注原文字数），落选稿的要点／风险／验收点不另存。

只配了一个员工时，两种方式完全一样（没有第二稿可融，也不会多那次调用）。

### 跳过环节

**任何环节都可以整个跳过。** 两条入口，都收中英文环节名：

```jsonc
// settings.json 顶层
{ "efftaskSkipSteps": ["质疑讨论", "验收"] }
```

```bash
/et 改个文案错别字。跳过质疑讨论和验收
```

两条入口**取并集**：配置文件说「一直跳质疑讨论」、提示词说「这次也跳验收」，两句都生效。（角色定义那边是覆盖语义——提示词点名了就换人；「谁来干」是单选，「干不干」是开关。）

> **跳过 ≠ 没配角色。** 这是最容易搞混的一点：
> - **没配角色** → 这一步**照常发生**，只是由当前主模型一个人干（集成验收会回落到验收席位）。唯二例外是测试验证和观察，它们本来就是 opt-in，不配等于不跑。
> - **跳过** → 这一步**整个不发生**，一次模型调用都没有。

跳过是**降低质量保证**的动作，所以启动关口不会只说「已跳过」，而是把后果逐条写出来让你在批准前看见：

| 跳过 | 关口会告诉你的后果 |
|------|-------------------|
| 分析 | 不出方案、不主动拆子任务，节点直接照目标开工。任务树基本只有根节点（执行者仍可动态加），深度和节点数上限因此失去意义 |
| 质疑讨论 | 方案没人质疑就进执行，漏项和隐藏依赖不会在这里被拦下 |
| 执行 | 没有人改代码，本次不会产生任何提交 |
| 测试验证 | 不实跑测试，验收只能读执行者的自述 |
| 验收 | 没人核对验收点，产出未经判断就合进集成分支 |
| 集成验收 | 子任务各自通过就算父任务达成，当初拆漏了不会再有人发现；而且所有**拆分型**节点（含根节点，如果它被拆了）不再评分。执行型节点的评分照常发生，所以单节点的 run 仍然有分 |
| 观察 | 不打分，低分触发的那一轮返工不会发生 |

关口还会当场拦下三个**跑不完**的组合：

- **跳过执行但不跳验收** —— 本次不会有任何代码改动，而验收席位仍会照常开会去核对这个空产出。判通过就等于给一个什么都没做的节点盖章并合进集成分支；判不通过就烧完验收迭代后阻断
- **跳过分析但不跳质疑讨论** —— 评审席位去评一份空方案，烧完迭代次数后阻断
- **七个全跳** —— 一次模型调用都没有，也不会有任何代码改动

被跳过的环节**不会**在 `node.md` 的评审/验收日志里留一条 PASS——一条假的通过记录会让你事后以为有人看过。它记的是「已跳过」。

预估调用数会跟着归零：**被跳过的环节按 0 次算**，而不是按「没配角色也跑一次主模型」算。注意这不等于「跳一半环节数字就掉一半」——没配角色的测试验证/集成验收/观察本来就计 0，跳它们对数字没有影响；真正省下来的是分析、质疑讨论、执行、验收这几个默认会跑的。

### 用提示词临时改配置

不想改文件时，直接在指令里说：

```bash
/et 重构登录模块。评审用 opus-架构 和 ds-安全，测试验证交给 ds-测试，过半通过就行
```

提示词里**指名了员工**就按提示词换人（是真的换掉，不是再加一个）；没指名就沿用配置文件里的人。产出/作用以提示词为准。

### 三条护栏

多员工会把调用数**乘**起来，所以有三条护栏。它们不在 `settings.json` 里，用自然语言在指令里说即可，关口会把最终取值显示给你确认：

| 护栏 | 默认 | 怎么说 |
|------|------|--------|
| 每环节席位上限 | 5 | 「每阶段最多 3 席」 |
| 通过门槛（比例） | 100%（全票） | 「过半通过就行」「三分之二通过」 |
| 通过门槛（人数） | 无 | 「至少 2 个人通过」 |

> **为什么需要放宽门槛**：默认是全票——任一席位提出阻断，整体就不通过。席位越多越难通过：每席独立 80% 通过率的话，3 席是 51%，9 席只有 13%。所以配了多个员工之后通常要同时放宽门槛，否则「人多」反而让任务跑不完。

启动关口会显示预估调用数上限，例如 `预估上限 2400 次模型调用(每节点最多 24 次 × 节点上限 100;实际通常远低于此)`。这是**上限口径**——按节点数上限算，实际任务通常只有几个节点，真实用量往往低两个数量级。它不是并发数。

### 常见坑

- **`roles[]` 是严格校验的**：写入未声明的字段会让**整条员工被跳过**（表现为「这个员工不存在」），而不只是该字段失效。原因会显示在 `/et` 启动关口的「你的请求中有以下部分不会生效」那一块里（非交互 `--print` 模式下才走终端）——**交互式会话里终端上看不到它**：ink 的 `patchConsole` 把 `console.error` 改写成了只进 debug 日志。
- **`step` 写错**会被拒绝并列出合法值，还会猜一个最接近的（写「测试」会提示「是不是想写『测试验证』」）。
- **`staff` 里的员工名找不到** → 该角色改由主模型兼任，关口会说明。这和「没写 staff」是两回事。
- **`execMode: 'cli'` 的员工** `/et` 目前派发不了，会被剔除并说明。
- **想让某一步别跑，要用「跳过」而不是「不配角色」**：不配角色只是换主模型一个人干，那一步照跑。见上面的「跳过环节」。
- **MCP 在所有环节都能用，但会写的 MCP 挡不住**：内建写工具（Edit/Write/Bash）只有执行环节有，而 `mcp__*` 无法从名字判断读写，给评审／验收席位配带写能力 MCP 的角色时它可以自己改完再放行。关口会提示。详见 `docs/roles-setup.md` 的「各环节能用什么工具」。

### 断点续跑

```bash
/et --resume            # 列出可恢复的 run
/et --resume 003        # 继续指定的 run
/et --resume 003 --retry-blocked   # 顺便重开被安全阀停下的节点
```

任务树持久化在 `.claude/efftask/<run-id>/`，是一棵和任务树同构的 md 目录。跑完但还没处置集成分支时，`--resume` 会重新弹出收口关口。

### 重做：让跑歪的任务重来一遍

跑完之后发现某个任务做错了——方案就跑偏了、执行没达到验收点、或者反复返工三轮之后被阻断。

在有重做之前，唯一的办法是 `--retry-blocked`。它的粒度是**整个运行**：所有被安全阀挡住的节点一起重开，而且只对「被阀门挡住」的节点有效。一个已经验收通过、但你看了不满意的节点，没有任何入口。

**怎么用**：run 结束后（不管是完成还是被阻断），在任务树上用 `↑↓` / `jk` 选中要重做的节点，按 **`r`**。节点详情页里也能直接按 `r`，不用先退回树上——详情页正是你判断「这个节点哪儿错了」的地方。

关口最多**三屏**：先选粒度，再选环节，最后看后果再确认。选「任务重做」时跳过中间那屏（它只对应一个环节），所以是两屏。

#### 第一屏：任务重做，还是阶段重做

| 粒度 | 做什么 |
|------|--------|
| **任务重做** | 重新分析并拆分，然后**照常往下跑完**（分析 → 质疑讨论 → 执行 → 验收，按你本次配置算）。有子任务时**先删掉整棵子树**，重做完按新方案重建。这是唯一一个不可逆的动作，删几个、其中几个已验收，第一屏就写着 |
| **阶段重做** | 从某一个环节重新开始。这一行会直接列出**本节点可选哪几个环节**——进去才发现全灰是白走一趟 |

分两级不是排版偏好：任务重做会删子树，阶段重做只重跑一个环节，代价差着数量级。并排放在同一张单子上时，选错一行的后果完全不同。

#### 第二屏：六个环节，四条按不动

| 入口 | 做什么 | 什么时候不可用 |
|------|--------|---------------|
| **从「质疑讨论」重做** | 保留现有方案，先重跑一次质疑讨论；**通过之后本节点会照常往下跑**（执行型接执行 → 验收，拆分型接集成验收）。**不通过就阻断并附评审意见**，不会自动重出方案 | 本节点还没有方案时不可用（没有可评审的东西） |
| **从「执行」重做** | 方案保留，重跑执行那一整段 | 拆分任务不可用，屏幕上写的是：这是拆分任务，它自己没有执行环节 —— 真正干活的是它的子任务 |
| **从「测试验证」重做** | —— | 永远不可用。理由**按你的配置算**：没给它配角色时写的是「本次运行没有测试验证环节（没给它配角色），重做也不会跑它 —— 要启用请先在 roles 里配席位」；配了席位才写「测试验证跑在执行环节内部，没有自己的入口 —— 要重跑它请选「从执行重做」」 |
| **从「验收」重做** | —— | 永远不可用，同上：验收跑在执行环节内部，没有自己的入口 —— 要重跑它请选「从执行重做」 |
| **从「集成验收」重做** | 子任务全部保留，只重新裁决一次「合起来达没达成父目标」 | 叶子任务不可用，屏幕上写的是：没有子任务，不存在集成验收 |
| **从「观察」重做** | —— | 永远不可用，理由同样按配置和节点形态算：没配角色时说这次没有这个环节；配了的话，执行型节点指向「从执行重做」，拆分型指向「从集成验收重做」 |

不可用的条目**仍然列在屏幕上**，只是按不动，并写明**去哪儿重跑**——而且指过去的那一条在同一个节点上一定是按得动的（拆分任务上不会把你指到同样是灰的「从执行重做」）。这样菜单不会随节点类型忽隐忽现，你也看得见为什么这里不能这么做——而且「只说不可用」是半句话：你想重跑的那件事通常还是做得到的，只是入口在别处。

> **为什么七个环节里只有四个能进，而且其中一个在上一级。** 能单独重入的点由状态机的形状决定：`advanceableKind` 只认三个座位——`CREATED`（分析和质疑讨论都从这里进）、`READY`（执行）、`WAITING_CHILDREN`（集成验收）。测试验证、验收、观察全都跑在这三个之内。
>
> 所以菜单里给一个**能按下去**的「验收重做」会是假的：已验收节点的隔离工作区在通过那一刻就被放掉了，重新建出来的是集成分支最新状态（含此后所有兄弟合入的改动）；通过之后那次空合并还会往执行自述里永久追加一句「该节点没有向集成分支贡献任何改动」，而它对一个确实贡献过的节点是假的、并且会被喂进之后每一次验收提示词；验收不通过更会直接回到执行者。三条假话换一个条目，不值。
>
> 屏幕上那句话是按**这个节点自己的名册**算的，不是 run 配置——`--resume` 时新加的席位不会落到已验收节点上，拿 run 配置去算就会承诺一个这个节点上根本不存在的环节。没配验证和观察角色时它写的是「执行 → 验收；不跑：测试验证、观察（未配置角色，这些环节不存在）」，而不是一句无条件的三步。

#### 父任务重做：先删子树

对一个有子任务的节点做**任务重做**时，**整棵子树会被删掉**，重做完按新方案重建。

这不是可选的。子任务的 id 由「父 id + 序号 + 标题」推导，留着旧子树重新拆分时：标题相同的会**覆盖**旧节点（可能覆盖掉已经验收通过的）；标题不同的会留下一批永远等不到的幽灵兄弟，父任务从此卡在「等子任务」。

**依赖会被重新修订**：子树**外面**还指着被删节点的依赖，会改指到被重做的父任务，而不是删掉——删掉的话下游会立刻起跑，而它要的东西所在的子树还没重建出来。两种例外：父任务自己指向某个后代的那条直接删掉（自依赖不是依赖，是死锁）；改指之后会**成环**的也删掉，并在确认屏上告诉你「N 条依赖被移除（下游可能比预期更早起跑）」——死锁比早起跑严重得多。

#### 确认屏会摊开后果

按下 `r` 选完环节之后，在真正执行之前你会看到：这个任务将重新走哪些环节、会删掉几个子任务（其中几个已验收）、被删子任务的 id 清单（超过 6 个会说清一共多少）、几条依赖被改写、几条被移除、释放几个隔离工作区、上级几个任务要重做集成验收、返工计数清零。

还有三件按下去之前很容易看不见的：

- **已验收的节点会退出终态**——屏幕上写着「本节点从「已验收」退回重跑 —— 在它重新通过之前，本次运行不再算完成」。你是在「✓ 高效任务完成」那一屏上按的 `r`，很容易以为这只是加跑一轮。
- **「释放隔离工作区」对一个脏工作区不是清理**。里面**未提交**的改动会先被固化到 `efftask/<run>/salvage/…` 分支再重置目录——不会丢，但不在原处了。
- **写进执行自述的那句重做注记按产出去哪儿了分两种**。已验收的节点写的是「产出此前已合入集成分支，在当前工作区里**能看到**它 —— 请在它之上继续改，不要从零重做」；没走到验收的才写「产出**不在**当前工作区里」。写反了的后果是执行者要么去找一个不存在的文件，要么把一份已经在那儿的产出从零再做一遍。

以及**这次重做做不到的事**，用 ⚠ 标出来：

> ⚠ N 个已验收子任务的代码**已经落进代码**（有隔离时已合进集成分支，没隔离时就在你的工作区里），删除任务不会回滚这些改动；新方案要么在它们之上继续，要么你先自己 revert

这一条特别重要：**删任务删的是任务记录，不是 git 提交。** 每个执行型子任务是在自己通过验收那一刻就合进集成分支的。

#### 上级任务会被一并重开

重做一个子任务时，它上面那条链（直到根任务）会被放回「等子任务」的状态，并重新做一次集成验收。这不是副作用，是必须的：不重开的话，调度器拒绝挑选任何祖先被阻断／已终结的节点，重做会**一次模型调用都不发生**；而且祖先那句「子任务合起来达成了父目标」判的是**旧产出**，子任务重做之后它不再成立。

**例外**：阻断理由是「依赖节点缺失 / 子节点缺失 / 依赖成环」的祖先**不会**被重开。那不是「某个环节失败了」，是这棵树自己对不上，重开只会让一批上游无法核实的工作跑起来，而运行报告成功。

被删节点的隔离工作区会被释放，但**脏的或者还没合入的会被拒绝删除**，并把路径告诉你（`⚠ xxx 的工作区保留在 /path：仍有未合入集成分支的提交`）。重做不该顺手毁掉你还没合并的产出。

#### 三种用不了的情况

| 情况 | 会怎样 |
|------|--------|
| **运行中** | 树上没有 `r` 键。要动一个失败节点，先按 Esc 中断，再 `/et --resume` |
| **被 Esc 中断过的 run** | 按 `r` 会被挡下，并告诉你去 `/et --resume <run id>`。中断标记对整个 `/et` 进程有效且撤销不掉，直接重做会立刻再阻断一次 |
| **只查看模式** | `--resume` 时选了「仅查看不继续」，不给重做——那个 run 的编排器没起来过，重做等于替你决定把它跑起来 |

底部提示行会跟着变：能重做时写着 `r 重做选中的任务`，不能时那几个字不出现。写一个不存在的键比没有这个键更糟。

#### 落盘失败会怎样

重做的落盘分三步：**放隔离工作区 → 删子树 → 写节点**。任何一步出问题都会显示在结束屏上，而不是只写进日志——比如 `X 的记录没删掉（下次恢复会复活它）`：一个删不掉的 `node.md` 会在下一次 `--resume` 时自己长回来，而你是唯一能处理它的人。如果**删了子树但父节点没写回去**，还会多一句：下次 `--resume` 会以「子节点缺失」阻断，以及怎么手工修。

#### 和 `--retry-blocked` 的区别

| | 重做（`r`） | `--retry-blocked` |
|---|---|---|
| 粒度 | 一个节点、一个环节 | 整个运行，所有被阀门挡住的节点 |
| 适用 | 任意节点，**包括已验收通过的** | 只对被安全阀挡住的节点有效 |
| 什么时候用 | 你看了结果不满意，或者知道哪一个节点错了 | run 因为撞上限整体停了，想整轮再来 |

节点连续返工撞满 `caps.maxIterations`（默认 3）被阻断时，`r` → 「从执行重做」是最省的出路：**验收记录保留**（它是返工提示词的反馈来源，清掉等于让执行者从零开始猜），但预算清零。

### 界面：任务树和详情页

**任务树**

| 键 | 做什么 |
|---|---|
| `↑↓` / `jk` | 上下移动 |
| `←` / `→` | 折叠 / 展开子树 |
| 空格 | 折叠状态切换 |
| 回车 | 打开光标那一行的详情页 |
| **鼠标点击** | 和在那一行按回车完全一样：光标移过去 + 打开详情页 |
| `r` | 重做（run 结束后才有） |
| `p` / `i` / `x` | 暂停调度 / 追加一句指令 / 取消光标选中的那个节点（只在运行中有） |
| `Esc` / `q` | 退出 |

**鼠标点击要终端在报告点击才有用**，而这需要全屏模式（`CLAUDE_CODE_NO_FLICKER=1`）——
非全屏时终端根本不发这些序列。所以任务树页脚只在真的能点时才写「回车/点击看详情」：
那一行是截断的，多塞一句「需要开全屏」会把右边的「Esc/q 退出」吃掉。
「为什么点不了」写在详情页页签条的右边；窄终端上那里也放不下整句时会退化成 `鼠标✗`。

**详情页**分成两个页卡，页签条在最下面：

- **任务**：目标 / 完整方案 / 重点 / 风险点 / 验收点 / 执行状态 / 依赖 / 阻断原因 / 评分 / 迭代次数 / 各阶段耗时 / **模型用量** / 评审记录 / 验收记录 / 隔离工作区
- **子 agent 输出**：每次模型调用一条流，带署名（哪个环节、第几轮、哪个员工、什么模型）

| 键 | 做什么 |
|---|---|
| `←` / `→` | 换页卡 |
| **鼠标点击页签** | 换到那个页卡 |
| `Tab` | 焦点在「页签条」和「内容区」之间切；焦点在页签条上时回车/空格进入内容 |
| `↑↓` / `jk` | 任务页卡：选段落；输出页卡：滚动 |
| 空格 | 任务页卡：展开/收起选中的段落；输出页卡：折叠/展开选中的那条流 |
| `^u` / `^d` | 任务页卡翻页 |
| `g` / `G` | 输出页卡到顶 / 到底（到底会恢复跟随最新） |
| `n` | 输出页卡换一条流 |
| `t` | 输出页卡展开选中那条流的思考原文（默认折叠成段数——思考会把工具调用淹掉） |
| `Esc` / `q` | 返回任务树。**任何时候都能返回**，没有死角 |
| `r` | 重做本任务（run 结束后才有） |

**详情页只在全屏模式下真的满屏。** 全屏时它渲染在 Claude Code 的模态槽里，可用行数是
`终端行数 - 3`，能吃满。非全屏时它**刻意留 8 行余量**给上面的对话——占满会让每秒一次的
耗时刷新逼出整屏重绘，而且被切掉的是顶部（标题和目标），和全屏正好相反。

终端窄到排不出可读内容时（内容区不足 20 列），详情页会直接说「终端太窄」，而不是硬排——
硬排的后果是行回流、最后一行被静默剪掉，而画面的总行数一点没变。

**模型写的那几段按 markdown 上色**：目标 / 完整方案 / 重点 / 风险点 / 验收点 / 执行状态 / 评审记录 / 验收记录。

标题、加粗、行内代码、列表、引用走的是主 REPL 那一套（复用的就是那份 `formatToken`）。

**有两处不一样，先说清楚，免得这句话自己变成假话**：主对话流把表格交给 `MarkdownTable`
这个 React 组件（按终端宽度分列宽、格内折行、太高转竖排），代码块还带语法高亮；而详情页
是按行出字符串的，用不上组件，也不做异步的语法高亮。所以这儿的**表格排得下才用对齐版、
排不下退回你写的原文**（对齐版不看窗口宽度，硬排会撑到一百多列、续行还丢掉行首的 `|`），
**代码块**保留围栏并把围栏压暗，正文不上色。

**任务清单**（`- [x]` / `- [ ]`）保留勾选标记 —— `formatToken` 会把它整个剥掉，
于是「已完成」和「未完成」长得一模一样。

**折叠预览里不留空行**：一段只给 3~6 行时，空行就是一半的篇幅。展开之后照留。

**机器生成的那几段一个记号都不动**：依赖 / 阻断原因 / 评分 / 迭代次数 / 各阶段耗时 / 模型用量 / 隔离工作区。

它们里面是 id、路径、`--flag`、`[WAITING_CHILDREN]`——交给 markdown 解析器只会被吃掉记号。
阻断原因还额外有一层语义红色，那层颜色不能被顶掉。

终端不支持颜色时（`chalk.level === 0`，比如管道重定向）**整个不上色，原文原样出**——
剥掉 `##` 和 `**` 又不上色是纯粹的信息损失。

### 模型用量：每个任务花了多少

详情页的「模型用量」一段回答两个问题，有子任务时给两行：

```
本节点: 4 次调用 · 11.0k tokens · 输入 10.0k / 输出 1.0k
含 3 个子任务（整棵子树）合计: 27 次调用 · 214.5k tokens · 输入 60.0k / 输出 9.5k · 缓存 读 143.0k / 写 2.0k
```

- **一次调用 = 上游的一条消息**，不是「一个环节」也不是「一个席位」：一席在工具循环里
  跑十轮就是十次调用，那十轮的钱是真花了的。
- **子树合计是读的时候现算的**，不落盘。存合计的话，一个节点的用量变化要同时改它到根的
  每一个祖先，而这条链上任何一次崩溃或重做都会让那些数字永久对不上，却没有任何东西会报错。
- **缓存读写单列**。它在计费上便宜一个数量级，但总量那一格是**全量**——一个高度复用
  上下文的运行，缓存读常常就是大头，漏掉它这个数字等于没有。OpenAI 两条协议上，
  `cached_tokens` 会从「输入」里减出来单列，口径和 anthropic 协议一致。
- **重做不清零**。钱花掉了就是花掉了 —— 任务重做会删掉整棵子树，那部分的账**记在重做目标身上**
  （详情页多一行「已废弃(重做删掉的子任务)」），所以表头那个总数不会因为一次重做而倒退。

任务树上也有：每一行末尾的 `⇅12/34.5k` 是**含子任务**的合计（折叠着的拆分节点，人想
知道的正是「这一整块花了多少」），表头的 `⇅120 次 · 1.2M tokens` 是整趟的合计。
窄终端上行里那个标记会**整个让位给标题**——树行回答的第一个问题永远是「这是哪个任务」。

**这个数是下限，不是全账**：只统计经过 `/et` 派发层的调用。漏在外面的是——

- **子 agent 里的自动压缩**。它对子 agent 不设防，而一次压缩就是一次读满上下文窗口的完整调用；
  它的产出以 `UserMessage` 回到主循环，**不是 assistant 消息**，这一层一条都看不见。执行档最容易把窗口撑满。
- 启动关口那次一次性的配置提取调用（1 次，量级可忽略）。
- 根方案起草失败时，那一趟的账随被丢弃的 root 对象一起没了。

**误差不是一个常数，而是随「有没有压缩过」阶跃的**：没压缩过的运行在 1% 以内；压缩一次就多漏
一个上下文窗口（200k 模型上约 150k~180k 输入），一趟总量 1~5M 的运行里每压缩一次约多漏 3%~10%。

子 agent 自己再开 Task 也不走这条路，不过默认配置下 `ALL_AGENT_DISALLOWED_TOOLS` 把 Task 挡在
子 agent 之外，所以它发生不了。provider 报错那种合成消息也不算一次调用——算进去的话「调用次数」
会随着报错次数虚涨，而那正是你想拿它判断的东西。

### 子 agent 输出里能看到什么

每一次模型调用一条流，里面按到达顺序是：模型说的话、它调了什么工具（含 `mcp__*`，
显示成 `<服务器> - <工具名> (MCP)(参数)`）、工具返回了什么、报没报错、以及**这次调用花了多久**。

```
▾ 方案 第1轮 · 架构师 (deepseek-reasoner)              ◐ 运行中 · 2 工具 · 12s
│ ✻ 思考 3 段（t 展开）
│ 我查一下仓库里未关闭的 issue。
│ ● gitlab - List Issues (MCP)(acme/web)
│ ● ctx7 - resolve-library-id (MCP)(react-router)
│   ⎿ gitlab - List Issues (MCP)(acme/web) · 1.8s · #412 登录页 500
│   ⎿ ctx7 - resolve-library-id (MCP)(react-router) · 900ms · MCP error -32001
```

**跑完的流默认是折叠的**（`▸`），只留一行「最新: …」——一次运行会开几十条流，全铺开就没法看了。
折叠那一行同样带归属和耗时：`▸ 方案 第1轮 · 架构师  ● 已完成 · 2 工具 · 12s` /
`│ 最新: ⎿ Bash(bun test) · 1.8s · 2043 pass`。按空格展开选中的那条。

页签上的 `(N 次调用)` 是**这个节点开过几次模型调用**（一次调用一条流），不是 agent 数；
上限 40 条，超了会把最旧的已收口流压成「只留表头和最后几条」。

并行调用时返回是错序到的，所以每条 `⎿` 会写清自己属于哪一次调用；紧跟在自己调用行
下面时就省掉不写。耗时量的是「调用发出到返回」的墙钟——**包含等你批准工具权限的时间**，
和主 REPL 一个口径。这句口径在输出页卡的页脚上也写着，免得一个等了十分钟批准的
`Bash` 被读成「这个测试跑了十分钟」。

**模型说的话也按 markdown 上色**（思考正文同样，而且仍然是暗的——少了那层暗色就分不清
哪句是想的、哪句是说的）。**工具调用行和工具返回行不上色**：里面全是路径、`--flag`、
`[TAG]`，解析一遍只会被改写。**代码围栏（```）里也不上色**，围栏行本身照原样画出来——
删掉它人就分不清代码从哪开始。

**OpenAI 协议的员工也能看到思考。** 兼容后端把推理放在 `reasoning_content`
（DeepSeek / Kimi / GLM / 通义 / MiniMax / vLLM）或 `reasoning`（OpenRouter 等）字段上，
这些默认就有，不需要配 `thinkingDepth`；`thinkingDepth` 在这条协议上译成 `reasoning_effort`，
只对「把推理藏在这个参数后面」的网关有意义。OpenAI 自家的 `chat/completions`
**不暴露推理正文**，所以真 OpenAI 后端在这条协议上没有思考可显示。

**要看真 OpenAI 的思考，用 `apiProtocol: "openai-responses"`。** Responses API
（`{apiUrl}/responses`）会给出推理摘要，这条桥把它渲染成思考内容。它还要求带工具调用的
轮次把上一轮的推理片段一起回传，否则上游 400——这件事由桥自己处理（`store: false` +
`include: ['reasoning.encrypted_content']`，密文搭 thinking 块的签名往返），你不用配任何东西。

**三种协议收得下的思考档位不一样**，写不进去的会被翻译，而且会在 `/et` 启动关口上说出来：
`xhigh` 两边协议都收；`max` 是 Anthropic 独有的，在 OpenAI 两条协议上译成 `xhigh`；整数只有
anthropic 收。Anthropic 协议下模型不支持 effort 参数时（比如 `claude-3-5-sonnet-20241022`），
这个值**整段不发**——关口上会写明。详见 `docs/roles-setup.md`。

**员工配置写错时不再一言不发。** 协议名少写一个字母、`thinkingDepth` 写成认不出来的值，
以前的表现是「这个员工不存在」而屏幕上零提示（`console.error` 被 ink 的 `patchConsole`
吞进 debug 日志了）。现在这些原因会出现在 `/et` 启动关口的「你的请求中有以下部分不会生效」
那一块里。

## 自行编译

```bash
bun install

# 打包成单个 JS（需要目标机器有 bun）
bun run build            # → dist/cli.js

# 编译成单文件二进制（目标机器什么都不需要）
bun run build:compile    # → dist/claude-haha

# 交叉编译
bun run scripts/build.ts --compile --target bun-windows-x64 --outfile claude.exe
```

版本号来自构建时的环境变量，不注入则是 `999.0.0-local`：

```bash
CLAUDE_CODE_LOCAL_VERSION=v0.1.0 bun run build:compile
```

### 关于 `vendor/zod-v4.js`

仓库里提交了一份**压平后的 zod**。原因：bun 1.3.14 给 zod 的 `export *` 链生成的懒导出表会引用不存在的符号，主构建产物一跑就 `ReferenceError: _uppercase2 is not defined`（不是重复打包——产物里只有一份，而且单独打包 zod 完全正常）。先把它压平成一个文件、主构建再指向那一份，就绕开了出问题的那条 codegen 路径。

升级 zod 之后重新生成：

```bash
bun run vendor:zod
```
