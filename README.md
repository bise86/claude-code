# Claude Code Haha

<p align="right"><strong>中文</strong> | <a href="./README.en.md">English</a></p>

基于 Claude Code 泄露源码修复的**本地可运行版本**，支持接入任意 Anthropic 兼容 API（如 MiniMax、OpenRouter 等）。

> 原始泄露源码无法直接运行。本仓库修复了启动链路中的多个阻塞问题，使完整的 Ink TUI 交互界面可以在本地工作。

<p align="center">
  <img src="docs/00runtime.png" alt="运行截图" width="800">
</p>

## 功能

- 完整的 Ink TUI 交互界面（与官方 Claude Code 一致）
- `--print` 无头模式（脚本/CI 场景）
- 支持 MCP 服务器、插件、Skills
- 支持自定义 API 端点和模型
- 降级 Recovery CLI 模式
- **高效任务模式 `/et`**：把需求拆成可并行、带依赖、多角色评审的任务树（[用法](#高效任务模式-et)）
- **飞书集成**：确认关口、权限请求、升级通知都可以在飞书卡片上处理

## 快速开始

### 方式 A：下载编译好的二进制（不需要装 Bun）

从 [Releases](https://github.com/bise86/claude-code/releases) 下载对应平台的单文件二进制：

| 平台 | 文件 |
|------|------|
| Linux x64 | `claude-haha-linux-x64` |
| macOS Apple Silicon | `claude-haha-darwin-arm64` |
| macOS Intel | `claude-haha-darwin-x64` |
| Windows x64 | `claude-haha-windows-x64.exe` |

```bash
chmod +x claude-haha-linux-x64
./claude-haha-linux-x64 --version
```

二进制里已经打包了运行时和全部依赖，机器上不需要 Bun 和 node_modules。但**仍然需要配置 API 凭据**——见下面第 3 步，把 `.env` 放在二进制同目录，或直接用环境变量。

### 方式 B：从源码运行

### 1. 安装 Bun

本项目运行依赖 [Bun](https://bun.sh)。如果你的电脑还没有安装 Bun，可以先执行下面任一方式：

```bash
# macOS / Linux（官方安装脚本）
curl -fsSL https://bun.sh/install | bash
```

如果在精简版 Linux 环境里提示 `unzip is required to install bun`，先安装 `unzip`：

```bash
# Ubuntu / Debian
apt update && apt install -y unzip
```

```bash
# macOS（Homebrew）
brew install bun
```

```powershell
# Windows（PowerShell）
powershell -c "irm bun.sh/install.ps1 | iex"
```

安装完成后，重新打开终端并确认：

```bash
bun --version
```

### 2. 安装项目依赖

```bash
bun install
```

### 3. 配置环境变量

复制示例文件并填入你的 API Key：

```bash
cp .env.example .env
```

编辑 `.env`：

```env
# API 认证（二选一）
ANTHROPIC_API_KEY=sk-xxx          # 标准 API Key（x-api-key 头）
ANTHROPIC_AUTH_TOKEN=sk-xxx       # Bearer Token（Authorization 头）

# API 端点（可选，默认 Anthropic 官方）
ANTHROPIC_BASE_URL=https://api.minimaxi.com/anthropic

# 模型配置
ANTHROPIC_MODEL=MiniMax-M2.7-highspeed
ANTHROPIC_DEFAULT_SONNET_MODEL=MiniMax-M2.7-highspeed
ANTHROPIC_DEFAULT_HAIKU_MODEL=MiniMax-M2.7-highspeed
ANTHROPIC_DEFAULT_OPUS_MODEL=MiniMax-M2.7-highspeed

# 超时（毫秒）
API_TIMEOUT_MS=3000000

# 禁用遥测和非必要网络请求
DISABLE_TELEMETRY=1
CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1
```

### 4. 启动

#### macOS / Linux

```bash
# 交互 TUI 模式（完整界面）
./bin/claude-haha

# 无头模式（单次问答）
./bin/claude-haha -p "your prompt here"

# 管道输入
echo "explain this code" | ./bin/claude-haha -p

# 查看所有选项
./bin/claude-haha --help
```

> `bin/claude-haha` **保持你敲命令时所在的目录**，所以可以（也应该）在你自己的项目里直接
> 调它的绝对路径：`/path/to/claude-code/bin/claude-haha`。项目级的 `.mcp.json`、
> `.claude/settings.json`、CLAUDE.md、git 仓库都按那个目录起算。
>
> （早前这个脚本会先 `cd` 到本仓库再启动，于是在一个配好 `.mcp.json` 的项目里
> `mcp list` 回答的是「No MCP servers configured」——读的是本仓库自己的目录。）

#### Windows

> **前置要求**：必须安装 [Git for Windows](https://git-scm.com/download/win)（提供 Git Bash，项目内部 Shell 执行依赖它）。

Windows 下启动脚本 `bin/claude-haha` 是 bash 脚本，无法在 cmd / PowerShell 中直接运行。请使用以下方式：

**方式一：PowerShell / cmd 直接调用 Bun（推荐）**

> **在你的项目目录里跑，不要先 `cd` 到本仓库**。项目级的一切都按当前工作目录起算：
> `.mcp.json`（项目级 MCP 服务器）、`.claude/settings.json`、CLAUDE.md、git 仓库。
> 站在本仓库里启动的话，这些会全部读到本仓库自己的那一份——`.mcp.json` 里配好的服务器
> 会表现为「No MCP servers configured」。把 `<REPO>` 换成本仓库的绝对路径：

```powershell
# 交互 TUI 模式
bun --env-file=<REPO>\.env --preload <REPO>\preload.ts <REPO>\src\entrypoints\cli.tsx

# 无头模式
bun --env-file=<REPO>\.env --preload <REPO>\preload.ts <REPO>\src\entrypoints\cli.tsx -p "your prompt here"

# 降级 Recovery CLI
bun --env-file=<REPO>\.env --preload <REPO>\preload.ts <REPO>\src\localRecoveryCli.ts
```

> `--preload` 不能省：`MACRO` 全局量由它注入，缺了启动就是
> `ReferenceError: MACRO is not defined`。（`bunfig.toml` 里那份 preload 只在 cwd 恰好是
> 本仓库时才生效，而这里恰恰不希望 cwd 是本仓库。）

**方式二：Git Bash 中运行**

```bash
# 在 Git Bash 终端中，与 macOS/Linux 用法一致
./bin/claude-haha
```

> **注意**：部分功能（语音输入、Computer Use、Sandbox 隔离等）在 Windows 上不可用，不影响核心 TUI 交互。

## 高效任务模式 `/et`

把一句需求拆成一棵**可并行、带依赖、多角色评审**的任务树，自动跑完。

```bash
/et 把登录模块重构成 JWT，补上测试
```

它会先弹一个**启动关口**让你确认：目标、并行数、名册（谁在什么环节干活）、预估调用数上限。确认之后自主执行，只在需要工具权限、触发安全阀、或合并冲突时才打扰你。跑完之后**自动把集成分支合并回你当前的分支**——产出就在当前目录里。工作区不干净、或者这一趟没正常跑完时不会自动合，屏幕上会说清原因和怎么手工来（分支原样保留，什么都不会丢）。

关口上有三个 git 开关，默认是**主干开发 + 不推远程**：

| 开关 | 键 | 默认 | 另一档 |
|------|----|------|--------|
| 隔离方式 | `w` | **worktree 隔离** —— 每个执行节点一个工作区，可以并行 | **共享工作树** —— 执行者直接改你当前目录，执行阶段强制串行、而且**不产生任何提交**（改动就摊在工作区里） |
| 收口方式 | `m` | **合回当前分支**（主干开发） | **保留 `efftask/<run-id>` 分支**（分支开发）——不自动合，跑完告诉你怎么 merge / 怎么发 PR |
| 自动推送 | `p` | **关** | 开了才 `git push -u origin`：收口方式是「合回当前分支」就推当前分支，是「保留分支」就推那条集成分支 |

三个选择都记进 `run.md`，`--resume` 会读回来并在恢复关口上显示（恢复时只读——这一趟的隔离方式在上一趟就定了，改它会让恢复出来的树和它的工作区对不上）。

**推送为什么默认关**：它是对外动作、不可撤销，而且我们不知道你的远程分支策略。合并只发生在你自己的仓库里，随时 `git reset` 得回来；推送不是。没开这个开关时，`--resume` 的收口关口里那个「推送分支」按钮仍然在，由你按。

**合并冲突先由模型自己解**，两处都是：

| 冲突发生在 | 谁来解 | 解不了怎么办 |
|------------|--------|--------------|
| 节点工作区 → 集成分支（运行中） | 该节点的执行角色，在它自己的工作区里解，**解完重跑一次验收**才允许合入 | 一次运行给 **6 次**（每一次都带着上一轮验收的否决理由再改一版）；用完才发升级卡等人工，而 `--resume` 回来额度**重新给满** |
| 集成分支 → 你自己的分支（收口） | 主模型，在你的检出里解 | 解完由 **git 复核**（还有未合并路径 / 暂存区里还留着冲突标记 / commit 不成，任何一条都算没解成）；不通过就 `git merge --abort` 把你的工作区还原到合并前，再照实告诉你 |

收口那次自动解决成功时，屏幕上会列出解了哪些文件、提醒这份解决**没有经过评审**，并给出一条可以照做的 `git reset --hard <合并前的 sha>`。

次数可以用一句话改：「解冲突给 10 次机会」→ `caps.mergeResolveAttempts: 10`（0–20）；说「冲突别自动解、直接叫我」就是 0——一撞上冲突直接等人工。不是默认值时启动关口的安全阀行会印出来。

### 严格度档位：分析和验收老是跑好几轮，多半不是标准太高

标准高不高之前，先看有没有人说过标准是什么。默认情况下验收环节的提示词里只有验收点和执行者的自述，一句「什么算通过」都没有——于是每个裁决席位各按自己的默认人格打分，而圆桌默认要**全票**才算通过。每席独立 80% 通过率的话，9 席全票通过的概率是 `0.8^9 ≈ 13%`：配的人越多，越跑不完。

`caps.strictness` 就是那把尺子，用一句话说出来即可：

| 说法 | 档位 | blocking 只填什么 | 测试验证 |
|------|------|------------------|----------|
| 「随便跑跑」「demo 而已」 | 初级 | 压根没做、做错了、跑不起来 | 没有可跑的手段时不判不通过（但要在 comments 里留痕） |
| 「按验收点来就行」 | 中级 | 验收点未达成、主路径有缺陷、没有任何证据 | 有手段而没跑 = 不通过 |
| 「严格点，不能有回归」 | 高级 | 再加上可预见的边界/错误路径、回归风险 | 没有可跑的手段 = 不通过；还要跑既有测试证明没回归 |
| 「生产级」「考虑并发和失败恢复」 | 专家 | 一切将来会咬人的：不变量、并发、吞错误、契约不一致 | 还要核对验证手段本身证明了什么 |

**不说就是不设档**，行为与不带这个特性时逐字节相同（全票 + 判据由各评审员自己把握）。注意现状**不等于**「专家档」——它是全票加判据空白，比任何一档都更严也更不可预测，同一份产出换个模型就换个结论。

档位同时也会放宽圆桌门槛（初级三分之一、中级过半、高级八成、专家全票），但**只在你自己没写过 `quorum`/`quorumSeats` 的时候**。实际要几席赞成：

| 席位 | 2 | 3 | 4 | 5 | 6 |
|------|---|---|---|---|---|
| 初级 | 1 | 2 | 2 | 2 | 3 |
| 中级 | 2 | 2 | 3 | 3 | 4 |
| 高级 | 2 | 3 | 4 | 4 | 5 |
| 专家 | 2 | 3 | 4 | 5 | 6 |

启动关口印的是**每一关实际席位数下的绝对门槛**，不是百分比，也不是四关取最大值——因为 80% 在 3 席上就与全票逐字节等价，而 review 5 席 / accept 2 席时印一个「4/5」对 accept 关是假的。放宽了的关列出来，其余的说「仍需全票」。

**运行中可以随时调**：`<` 放松一档、`>` 收紧一档，表头显示当前档位。改档不打断在飞的调用，从**下一场圆桌**开始生效，并写进 `run.md`（`--resume` 读得回来）。已经因为「迭代超限」阻断的节点不会因为降档自动复活——降档不退还已经烧掉的额度，按 `r` 重做才会按新档位重跑，重做关口会把这件事写在确认页上。

**降档降的是「多好才算够」，不降「到底做没做」。** 四个裁决环节都带一道与档位无关的地板。产出侧三关（测试验证／验收／集成验收）是：执行者没报告任何产出、报告里声称做了但找不到任何痕迹、裁决者自己没看过任何产出就要放行——任何一条都一律不通过。质疑讨论关有**自己那一份**（方案是空的／方案声称的做法找不到落点／没真读过方案就放行），因为那时一行代码都还没写，拿产出侧那三条去评审等于恒真判死。

一句诚实的话：这道地板是**提示词层的缓解，不是修复**。代码层今天挡不住一个零改动的执行叶子被判通过（空产出闸门只查字符串非空，`worktreePool` 对零改动返回「合并成功」），而这一点在有档位之前就成立——初级档改变的是概率，不是可达性。真正的结构性闸门（要求叶子分支相对集成分支有非空 diff）还不存在，它有自己的设计面（非隔离运行没有 diff 可取、纯文档节点会误伤），没有顺手挂在这个旋钮上。

### 两个核心概念：员工与角色

这两个词很容易混，先分清：

| 概念 | 是什么 | 配在哪 |
|------|--------|--------|
| **员工（staff）** | 一个**可派遣的身份**，自带模型、API 地址、工具集 | `settings.json` 的 `roles[]` |
| **角色（role）** | 任务里的一个**职能**，比如「架构师」「安全」 | `settings.json` 的 `efftaskRoles[]`，或直接写在提示词里 |

**多对多**：一个员工可以担任多个角色，一个角色也可以由多个员工担任。

一个角色配了多个员工时，他们**必须收敛成一个产出**——具体怎么收敛，取决于环节（见下）。

### 环节：任务的七个步骤

每个节点先被定为**拆分型**或**执行型**，再按形态走一串环节：

- **拆分型**：分析 → 质疑讨论 →（等全部子任务完成）→ **集成验收** → 观察
- **执行型**：分析 → 质疑讨论 → 执行 → 测试验证 → 验收 → 观察 →（自动合并进集成分支）

> **集成验收不做合并。** 合并早就发生了——每个执行型节点自己通过验收时，就把它的工作区合进了集成分支。集成验收判的是另一件事：**「这些子任务的结果合起来，达成父节点的目标了吗」**。所以它必须等全部子任务完成——少一块就问不了这个问题。它也是唯一能发现「当初拆漏了」的地方：裁决不通过时可以直接提出补救子任务，挂上去跑完再重新验收。
>
> 执行型节点的合并是**机械**的，没有角色关口。所以「集成验收」这个环节只对拆分型节点生效。

**自由的是角色，固定的是环节。** 你可以定义任意多个角色、任意取名、指定任意员工担当、写任意的产出与作用。不自由的只有一件事：这个角色挂在**哪个环节**上。环节是流水线状态机的骨架，它决定这一席什么时候被调用、能不能拿到写工具、`--resume` 之后还在不在。

> 环节列表**会随版本增长**——这一版就从 5 个长到了 7 个。写一个不存在的环节名会被明确拒绝并告诉你合法值，而不是静默丢弃。


### 角色字段

四个必填字段缺任何一个，该角色**不生效**，并在启动关口上说明原因（不静默丢弃）：

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | 是 | 角色名，任意取 |
| `step` | 是 | 在哪个环节用。见下表。旧键名 `stage` 仍然读得进来 |
| `output` | 是 | 产出什么 |
| `purpose` | 是 | 起什么作用 |
| `staff` | 否 | 由哪些员工担当。**省略 = 主模型兼任** |

`step` 的合法值（中文英文都收，落盘统一成英文）：

| 中文 | 英文 | 多员工时怎么收敛成一个产出 |
|------|------|--------------------------|
| 分析 | `plan` | **两种，可选**：顺序精化（默认）或方案融合圆桌。见下一节 |
| 质疑讨论 | `review` | **圆桌**：各自独立裁决，按通过门槛合成一个结论 |
| 执行 | `execute` | **只能一个员工**（物理约束：工作区路径不含员工维度） |
| 测试验证 | `verify` | 圆桌 |
| 验收 | `accept` | 圆桌 |
| 集成验收 | `integrate` | 圆桌。**只对拆分型节点生效**；没配时回落到验收席位。旧名「集成提交」仍可写 |
| 观察 | `observer` | **各自打分，取最低分**；其余人的理由一条不丢地记在旁边 |

### 分析环节：两种收敛方式

分析是唯一一个可以选收敛方式的环节，因为「多个人一起想方案」有两种截然不同的做法：

| 方式 | 怎么跑 | 什么时候用 |
|------|--------|-----------|
| **顺序精化**（默认） | 第一位起草，后面每一位在**前一稿上**修订。全程只有一份稿子 | 方向已经清楚，想要的是逐层加固 |
| **方案融合圆桌** | 每一位**独立**起草，互相看不到；然后由最后一席把所有稿子融合成一份最优解 | 方向还没定，怕第一稿把后面所有人锚死 |

顺序精化的代价是**锚定效应**：第一稿的框架基本就是最终框架，后面的人在修订而不是重想。融合圆桌拿掉了这个锚，代价是多一次模型调用（融合那次）。

在指令里说一句就能切：

```bash
/et 设计一套限流方案。分析用圆桌
```

融合席位是**最后一席**（名册里排在最后的那个员工），它拿到的是匿名化的「稿 A / 稿 B / 稿 C」——看不到谁写的，避免按人而不是按内容取舍。融合结果作为正式方案往下走，**落选的稿子不丢**：每份的方案正文存进 `node.md` 的「备选方案」段落，事后能查为什么没选它。存的是方案正文那一段（超长会截断并标注原文字数），落选稿的要点／风险／验收点不另存。

只配了一个员工时，两种方式完全一样（没有第二稿可融，也不会多那次调用）。

### 跳过环节

**任何环节都可以整个跳过。** 两条入口，都收中英文环节名：

```jsonc
// settings.json 顶层
{ "efftaskSkipSteps": ["质疑讨论", "验收"] }
```

```bash
/et 改个文案错别字。跳过质疑讨论和验收
```

两条入口**取并集**：配置文件说「一直跳质疑讨论」、提示词说「这次也跳验收」，两句都生效。（角色定义那边是覆盖语义——提示词点名了就换人；「谁来干」是单选，「干不干」是开关。）

> **跳过 ≠ 没配角色。** 这是最容易搞混的一点：
> - **没配角色** → 这一步**照常发生**，只是由当前主模型一个人干（集成验收会回落到验收席位）。唯二例外是测试验证和观察，它们本来就是 opt-in，不配等于不跑。
> - **跳过** → 这一步**整个不发生**，一次模型调用都没有。

跳过是**降低质量保证**的动作，所以启动关口不会只说「已跳过」，而是把后果逐条写出来让你在批准前看见：

| 跳过 | 关口会告诉你的后果 |
|------|-------------------|
| 分析 | 不出方案、不主动拆子任务，节点直接照目标开工。任务树基本只有根节点（执行者仍可动态加），深度和节点数上限因此失去意义 |
| 质疑讨论 | 方案没人质疑就进执行，漏项和隐藏依赖不会在这里被拦下 |
| 执行 | 没有人改代码，本次不会产生任何提交 |
| 测试验证 | 不实跑测试，验收只能读执行者的自述 |
| 验收 | 没人核对验收点，产出未经判断就合进集成分支 |
| 集成验收 | 子任务各自通过就算父任务达成，当初拆漏了不会再有人发现；而且所有**拆分型**节点（含根节点，如果它被拆了）不再评分。执行型节点的评分照常发生，所以单节点的 run 仍然有分 |
| 观察 | 不打分，低分触发的那一轮返工不会发生 |

关口还会当场拦下三个**跑不完**的组合：

- **跳过执行但不跳验收** —— 本次不会有任何代码改动，而验收席位仍会照常开会去核对这个空产出。判通过就等于给一个什么都没做的节点盖章并合进集成分支；判不通过就烧完验收迭代后阻断
- **跳过分析但不跳质疑讨论** —— 评审席位去评一份空方案，烧完迭代次数后阻断
- **七个全跳** —— 一次模型调用都没有，也不会有任何代码改动

被跳过的环节**不会**在 `node.md` 的评审/验收日志里留一条 PASS——一条假的通过记录会让你事后以为有人看过。它记的是「已跳过」。

预估调用数会跟着归零：**被跳过的环节按 0 次算**，而不是按「没配角色也跑一次主模型」算。注意这不等于「跳一半环节数字就掉一半」——没配角色的测试验证/集成验收/观察本来就计 0，跳它们对数字没有影响；真正省下来的是分析、质疑讨论、执行、验收这几个默认会跑的。

### 用提示词临时改配置

不想改文件时，直接在指令里说：

```bash
/et 重构登录模块。评审用 opus-架构 和 ds-安全，测试验证交给 ds-测试，过半通过就行
```

提示词里**指名了员工**就按提示词换人（是真的换掉，不是再加一个）；没指名就沿用配置文件里的人。产出/作用以提示词为准。

### 定向注入：点名给某个环节或某个角色的话

一句需求里往往混着几种话：整体目标、给执行者的约束、给评审员的关注点、给某个角色的特别
要求。它们**不该都进同一个地方**——在这之前整段提示词只有一个去处（根节点的目标），所以
「评审时重点看并发安全」这句话的实际去处是：根方案作者读到它，然后它被方案的产出覆盖掉，
**评审员一个字都看不到**（评审提示词只吃 `node.plan`）。

现在这类话会被抽出来，拼进对应环节 / 对应席位的提示词：

```bash
/et 把登录改成 JWT。评审时重点看并发安全，执行时别动 src/legacy，架构师要给出回滚方案
```

- 「评审时重点看并发安全」→ 质疑讨论环节的提示词
- 「执行时别动 src/legacy」→ 执行环节的提示词
- 「架构师要给出回滚方案」→ 名册里那个**角色**（或员工）的那一席

判据是这句话**冲着谁说的**，不是它讲什么。整体目标（「把登录改成 JWT」）不属于任何环节，
留在目标里——抄进每个环节等于让同一句话在每次调用里再出现一遍，白付钱。一句话同时点了
环节和人（「让架构师在评审时看并发」）算角色，更具体的那个赢。

**启动关口会把去处逐条显示出来**，这不是装饰：哪句话进哪个环节是一次抽取模型的判断，
抽错了运行会照常跑完，而你唯一能发现的方式是事后翻 `node.md`。关口存在的全部意义正是
「批准之前看见自己批准了什么」。飞书卡片上也有同一段——两个批准入口必须说同一件事。

三种不会生效的情况都会点名说出来（在「你的请求中有以下部分不会生效」那一块）：

| 情况 | 会说 |
|------|------|
| 环节名认不出来 | 「你对『测试』提的那段要求没有对应的环节……是不是想写『测试验证』?」 |
| 点给一个这次不会跑的环节 | 「你对『测试验证』提的那段要求不会生效：没给这个环节配角色，它这次不会发生」（被 `skipSteps` 跳过时同理） |
| 角色/员工名对不上名册 | 「你点名给『架构师』的那段要求不会生效：本次名册里没有这个角色或员工（名册上是：……）」 |

和重做时补的那句话一样，**裁决类环节会额外读到「它判的那件事」对应的那条**并被告知
「按补充后的意图判」（质疑讨论读分析那条，验收／测试验证／集成验收／观察读执行那条）
——理由和上面「补一句提示词给这次重做」里那段实测一样。

这两个字段（`phaseGuidance` / `roleGuidance`）会写进 `run.md` 并在 `--resume` 时读回来。
不读回的话第一次恢复就会静默清零：名册一模一样，而模型收到的东西变了。

**七个环节 + 两条容易漏的通道都收得到**：根节点在启动关口第三关起草的那次分析调用
（正常路径下根节点唯一的一次分析——批准之后运行会跳过它自己那次），以及**解合并冲突**
那次真正会写代码的调用。后者尤其要紧：你补一句「别动 src/legacy」而它收不到的话，
最可能去改那些文件的恰恰就是它。

### 三条护栏

多员工会把调用数**乘**起来，所以有三条护栏。它们不在 `settings.json` 里，用自然语言在指令里说即可，关口会把最终取值显示给你确认：

| 护栏 | 默认 | 怎么说 |
|------|------|--------|
| 每环节席位上限 | 5 | 「每阶段最多 3 席」 |
| 通过门槛（比例） | 100%（全票） | 「过半通过就行」「三分之二通过」 |
| 通过门槛（人数） | 无 | 「至少 2 个人通过」 |

> **为什么需要放宽门槛**：默认是全票——任一席位提出阻断，整体就不通过。席位越多越难通过：每席独立 80% 通过率的话，3 席是 51%，9 席只有 13%。所以配了多个员工之后通常要同时放宽门槛，否则「人多」反而让任务跑不完。

启动关口会显示预估调用数上限，例如 `预估上限 2400 次模型调用(每节点最多 24 次 × 节点上限 100;实际通常远低于此)`。这是**上限口径**——按节点数上限算，实际任务通常只有几个节点，真实用量往往低两个数量级。它不是并发数。

### 慢模型/思考模型：超时是怎么算的

一次调用有两条时钟，都跟着同一个旋钮 `caps.nodeTimeoutMs`（默认 10 分钟，直接说「阶段超时 20 分钟」就能调；关口上会显示成 `静默超时 20 分钟`，不足一分钟时显示秒）：

| 时钟 | 量什么 | 默认 | 开火时说什么 |
|---|---|---|---|
| 静默 | 多久**没有任何输出** | 10 分钟 | `静默超过该时长没有任何输出` |
| 总时长 | 这一次调用**总共**跑了多久（× 6） | 1 小时 | `一直有输出但迟迟不结束` |

总时长那条是为「滴水式上游」准备的——每分钟吐一个 token 的端点永远不会触发静默阀，而它和挂死是同一类故障，只是装得像在干活。两条都**不含等你批工具权限的时间**（那有自己的 7 天预算）。把 `caps.nodeTimeoutMs` 设成 0 会把两条一起关掉。

**流式增量算「有输出」。** 一个思考十分钟才说第一句话的模型不算静默——它一直在吐 token。（这一条以前是坏的：`runAgent` 只把**完整消息**交出来，思考期间的增量被丢掉，于是这条时钟实际量的是「两条完整消息之间的间隔」，一次长思考会被判成「静默超过 600000 ms 没有任何输出」。而主模型那条路上没有这条时钟，所以同一个模型当主模型正常、配成员工就老是报错。）

还有两条不是 `/et` 的时钟，遇到「员工模型老是超时而主模型正常」时值得知道：

- **等人批工具权限**不算进静默时长（它有自己的预算 `caps.humanTimeoutMs`，默认 7 天）。
- **走自己端点的员工**（`roles[]` + `execMode: 'api'`）多一条：翻译层要先嗅一口响应才知道是不是 SSE（不嗅的话，一次「成功但完全空白」的回答会被当成这一席的真实产出），所以「上游迟迟不发第一个字节」这段等待落在 **SDK 自己的请求超时**里——默认 10 分钟，只认环境变量 `API_TIMEOUT_MS`，`caps.nodeTimeoutMs` 调多大都动不了它。上游只在思考完成后才吐第一个字节、而思考超过 10 分钟时，把 `API_TIMEOUT_MS` 调大。

### 上游限流（429）会怎样

多角色圆桌是**并行**的，但受同一个全局并发池约束——池子上限就是你在关口上确认的并行数，「步骤 + 席位」共用它，不存在「3 席 × 5 并发 = 15 个并发调用」。

真正会让 429 变多的是限流**发生之后**的行为，这里有三条：

- **整趟 run 一起退避**。任何一次调用被上游限流（429/529），下一次调用（不管哪个节点、哪一席）都会先等冷却：2s → 4s → 8s …上限 60s，成功一次就归零。冷却期间那一席的输出窗里会写一行 `[上游限流,等 Ns 后再发这次请求]`。
- **重试只重派打不通的那几席**。圆桌里 3 席有 1 席调用失败时，重试只重发那 1 席，另外两席已经出的裁决原样留着（以前是整桌重开：3 席 × 3 轮 = 9 次调用换 3 次有效裁决，而且正好发生在上游让你慢下来的时候）。
- **分析环节的单次调用会重试 3 次**，执行环节**不重试**——执行者带写工具，一次 429 可能发生在它已经改过几个文件之后，重跑等于让第二个执行者对着一个半改过的工作区从头开始。它会带着「上游在限流」的阻断理由停下，`/et --resume` 可以继续。

还嫌频繁的话，两个旋钮都在关口上：把并行数调小（运行中按 `←`/`→` 也能调），或者把每环节席位上限调小。

### 常见坑

- **`roles[]` 是严格校验的**：写入未声明的字段会让**整条员工被跳过**（表现为「这个员工不存在」），而不只是该字段失效。原因会显示在 `/et` 启动关口的「你的请求中有以下部分不会生效」那一块里（非交互 `--print` 模式下才走终端）——**交互式会话里终端上看不到它**：ink 的 `patchConsole` 把 `console.error` 改写成了只进 debug 日志。
- **`step` 写错**会被拒绝并列出合法值，还会猜一个最接近的（写「测试」会提示「是不是想写『测试验证』」）。
- **`staff` 里的员工名找不到** → 该角色改由主模型兼任，关口会说明。这和「没写 staff」是两回事。
- **`execMode: 'cli'` 的员工** `/et` 目前派发不了，会被剔除并说明。它也不继承 MCP 和 CLAUDE.md（是另一个进程）——要怎么配通见「子 agent 继承什么：MCP 与 CLAUDE.md」。
- **想让某一步别跑，要用「跳过」而不是「不配角色」**：不配角色只是换主模型一个人干，那一步照跑。见上面的「跳过环节」。
- **所有环节拿的是同一份工具：会话里的全部工具（含 Edit/Write/Bash）加全部 MCP**。按环节分档已于 2026-08 取消。代价要知道：给评审／验收席位配的角色**可以自己把问题改掉再判通过**——「执行者与评审者分离」不再由工具清单保证。还拦着的只有两道行为闸门：测试验证环节前后比对工作区，动了就判该轮作废并返工；以及 `canUseTool` 的逐次询问。关口会提示。详见 `docs/roles-setup.md` 的「各环节能用什么工具」。

### 断点续跑

```bash
/et --resume            # 列出可恢复的 run
/et --resume 003        # 继续指定的 run
/et --resume 003 --retry-blocked   # 顺便重开被安全阀停下的节点
```

任务树持久化在 `.claude/efftask/<run-id>/`，是一棵和任务树同构的 md 目录。跑完但还没处置集成分支时（自动合并没做成、或者被阻断的那些），`--resume` 会弹出收口关口让你选合并 / 推送 / 保留 / 丢弃。

### 重做：让跑歪的任务重来一遍

跑完之后发现某个任务做错了——方案就跑偏了、执行没达到验收点、或者反复返工三轮之后被阻断。

在有重做之前，唯一的办法是 `--retry-blocked`。它的粒度是**整个运行**：所有被安全阀挡住的节点一起重开，而且只对「被阀门挡住」的节点有效。一个已经验收通过、但你看了不满意的节点，没有任何入口。

**怎么用**：run 结束后（不管是完成还是被阻断），在任务树上用 `↑↓` / `jk` 选中要重做的节点，按 **`r`**。节点详情页里也能直接按 `r`，不用先退回树上——详情页正是你判断「这个节点哪儿错了」的地方。

失败的节点还有两个**更快的**入口，`R` 和 `s`，见下面的「失败节点：两个快捷键」。

关口最多**三屏**：先选粒度，再选环节，最后看后果再确认。选「任务重做」时跳过中间那屏（它只对应一个环节），所以是两屏。

#### 第一屏：任务重做，还是阶段重做

| 粒度 | 做什么 |
|------|--------|
| **任务重做** | 重新分析并拆分，然后**照常往下跑完**（分析 → 质疑讨论 → 执行 → 验收，按你本次配置算）。有子任务时**先删掉整棵子树**，重做完按新方案重建。这是唯一一个不可逆的动作，删几个、其中几个已验收，第一屏就写着 |
| **阶段重做** | 从某一个环节重新开始。这一行会直接列出**本节点可选哪几个环节**——进去才发现全灰是白走一趟 |

分两级不是排版偏好：任务重做会删子树，阶段重做只重跑一个环节，代价差着数量级。并排放在同一张单子上时，选错一行的后果完全不同。

#### 第二屏：六个环节，四条按不动

| 入口 | 做什么 | 什么时候不可用 |
|------|--------|---------------|
| **从「质疑讨论」重做** | 保留现有方案，先重跑一次质疑讨论；**通过之后本节点会照常往下跑**（执行型接执行 → 验收，拆分型接集成验收）。**不通过就阻断并附评审意见**，不会自动重出方案 | 本节点还没有方案时不可用（没有可评审的东西） |
| **从「执行」重做** | 方案保留，重跑执行那一整段 | 拆分任务不可用，屏幕上写的是：这是拆分任务，它自己没有执行环节 —— 真正干活的是它的子任务 |
| **从「测试验证」重做** | —— | 永远不可用。理由**按你的配置算**：没给它配角色时写的是「本次运行没有测试验证环节（没给它配角色），重做也不会跑它 —— 要启用请先在 roles 里配席位」；配了席位才写「测试验证跑在执行环节内部，没有自己的入口 —— 要重跑它请选「从执行重做」」 |
| **从「验收」重做** | —— | 永远不可用，同上：验收跑在执行环节内部，没有自己的入口 —— 要重跑它请选「从执行重做」 |
| **从「集成验收」重做** | 子任务全部保留，只重新裁决一次「合起来达没达成父目标」 | 叶子任务不可用，屏幕上写的是：没有子任务，不存在集成验收 |
| **从「观察」重做** | —— | 永远不可用，理由同样按配置和节点形态算：没配角色时说这次没有这个环节；配了的话，执行型节点指向「从执行重做」，拆分型指向「从集成验收重做」 |

不可用的条目**仍然列在屏幕上**，只是按不动，并写明**去哪儿重跑**——而且指过去的那一条在同一个节点上一定是按得动的（拆分任务上不会把你指到同样是灰的「从执行重做」）。这样菜单不会随节点类型忽隐忽现，你也看得见为什么这里不能这么做——而且「只说不可用」是半句话：你想重跑的那件事通常还是做得到的，只是入口在别处。

> **为什么七个环节里只有四个能进，而且其中一个在上一级。** 能单独重入的点由状态机的形状决定：`advanceableKind` 只认三个座位——`CREATED`（分析和质疑讨论都从这里进）、`READY`（执行）、`WAITING_CHILDREN`（集成验收）。测试验证、验收、观察全都跑在这三个之内。
>
> 所以菜单里给一个**能按下去**的「验收重做」会是假的：已验收节点的隔离工作区在通过那一刻就被放掉了，重新建出来的是集成分支最新状态（含此后所有兄弟合入的改动）；通过之后那次空合并还会往执行自述里永久追加一句「该节点没有向集成分支贡献任何改动」，而它对一个确实贡献过的节点是假的、并且会被喂进之后每一次验收提示词；验收不通过更会直接回到执行者。三条假话换一个条目，不值。
>
> 屏幕上那句话是按**这个节点自己的名册**算的，不是 run 配置——`--resume` 时新加的席位不会落到已验收节点上，拿 run 配置去算就会承诺一个这个节点上根本不存在的环节。没配验证和观察角色时它写的是「执行 → 验收；不跑：测试验证、观察（未配置角色，这些环节不存在）」，而不是一句无条件的三步。

#### 父任务重做：先删子树

对一个有子任务的节点做**任务重做**时，**整棵子树会被删掉**，重做完按新方案重建。

这不是可选的。子任务的 id 由「父 id + 序号 + 标题」推导，留着旧子树重新拆分时：标题相同的会**覆盖**旧节点（可能覆盖掉已经验收通过的）；标题不同的会留下一批永远等不到的幽灵兄弟，父任务从此卡在「等子任务」。

**依赖会被重新修订**：子树**外面**还指着被删节点的依赖，会改指到被重做的父任务，而不是删掉——删掉的话下游会立刻起跑，而它要的东西所在的子树还没重建出来。两种例外：父任务自己指向某个后代的那条直接删掉（自依赖不是依赖，是死锁）；改指之后会**成环**的也删掉，并在确认屏上告诉你「N 条依赖被移除（下游可能比预期更早起跑）」——死锁比早起跑严重得多。

#### 确认屏会摊开后果

按下 `r` 选完环节之后，在真正执行之前你会看到：这个任务将重新走哪些环节、会删掉几个子任务（其中几个已验收）、被删子任务的 id 清单（超过 6 个会说清一共多少）、几条依赖被改写、几条被移除、释放几个隔离工作区、上级几个任务要重做集成验收、返工计数清零。

还有三件按下去之前很容易看不见的：

- **已验收的节点会退出终态**——屏幕上写着「本节点从「已验收」退回重跑 —— 在它重新通过之前，本次运行不再算完成」。你是在「✓ 高效任务完成」那一屏上按的 `r`，很容易以为这只是加跑一轮。
- **「释放隔离工作区」对一个脏工作区不是清理**。里面**未提交**的改动会先被固化到 `efftask/<run>/salvage/…` 分支再重置目录——不会丢，但不在原处了。
- **写进执行自述的那句重做注记按产出去哪儿了分两种**。已验收的节点写的是「产出此前已合入集成分支，在当前工作区里**能看到**它 —— 请在它之上继续改，不要从零重做」；没走到验收的才写「产出**不在**当前工作区里」。写反了的后果是执行者要么去找一个不存在的文件，要么把一份已经在那儿的产出从零再做一遍。

以及**这次重做做不到的事**，用 ⚠ 标出来：

> ⚠ N 个已验收子任务的代码**已经落进代码**（有隔离时已合进集成分支，没隔离时就在你的工作区里），删除任务不会回滚这些改动；新方案要么在它们之上继续，要么你先自己 revert

这一条特别重要：**删任务删的是任务记录，不是 git 提交。** 每个执行型子任务是在自己通过验收那一刻就合进集成分支的。

#### 上级任务会被一并重开

重做一个子任务时，它上面那条链（直到根任务）会被放回「等子任务」的状态，并重新做一次集成验收。这不是副作用，是必须的：不重开的话，调度器拒绝挑选任何祖先被阻断／已终结的节点，重做会**一次模型调用都不发生**；而且祖先那句「子任务合起来达成了父目标」判的是**旧产出**，子任务重做之后它不再成立。

**例外**：阻断理由是「依赖节点缺失 / 子节点缺失 / 依赖成环」的祖先**不会**被重开。那不是「某个环节失败了」，是这棵树自己对不上，重开只会让一批上游无法核实的工作跑起来，而运行报告成功。

被删节点的隔离工作区会被释放，但**脏的或者还没合入的会被拒绝删除**，并把路径告诉你（`⚠ xxx 的工作区保留在 /path：仍有未合入集成分支的提交`）。重做不该顺手毁掉你还没合并的产出。

#### 三种用不了的情况

| 情况 | 会怎样 |
|------|--------|
| **运行中** | 树上没有 `r` / `R` / `s` 键（编排器正握着这些节点）。要动一个失败节点，先按 Esc 中断，再 `/et --resume`。运行中能做的是 `p` 暂停、`i` 追加指令、`x` 取消某个节点、`+`/`-` 调并发 |
| **被 Esc 中断过的 run** | 按 `r` 会被挡下，并告诉你去 `/et --resume <run id>`。中断标记对整个 `/et` 进程有效且撤销不掉，直接重做会立刻再阻断一次 |
| **只查看模式** | `--resume` 时选了「仅查看不继续」，不给重做——那个 run 的编排器没起来过，重做等于替你决定把它跑起来 |

底部提示行会跟着变：能重做时写着 `r 重做选中的任务`，不能时那几个字不出现。写一个不存在的键比没有这个键更糟。

#### 落盘失败会怎样

重做的落盘分三步：**放隔离工作区 → 删子树 → 写节点**。任何一步出问题都会显示在结束屏上，而不是只写进日志——比如 `X 的记录没删掉（下次恢复会复活它）`：一个删不掉的 `node.md` 会在下一次 `--resume` 时自己长回来，而你是唯一能处理它的人。如果**删了子树但父节点没写回去**，还会多一句：下次 `--resume` 会以「子节点缺失」阻断，以及怎么手工修。

#### 补一句提示词给这次重做

确认屏上按 **`e`** 可以补一句话，它会被拼进提示词。去处**按粒度分**：

| 粒度 | 那句话给谁 |
|------|-----------|
| **任务重做** | 给这个任务的**每一个环节**（分析、评审、执行、验收……都看得到） |
| **阶段重做** | 只给**那一个环节**。比如「从执行重做」补的那句话只进执行提示词 |

写完回到确认屏，那句话会**印在后果清单里**——它会真的进提示词，而这是你按下确认之前
最后一次核对自己写了什么的机会。同一处再写一次是**替换**，不是追加（追加会让两条互相
打架，而模型看不出哪句更新）。它也会显示在详情页的「补充指引（你写的）」那一段里，
所以你随时能看到这个节点上此刻挂着哪几句话。

**裁决类环节会额外读到「它判的那件事」对应的那条指引**，并被告知「按补充后的意图判」：

| 裁决环节 | 它判什么 | 额外读到 |
|---------|---------|---------|
| 质疑讨论 | **方案**（那时一行代码都还没写） | 给「分析」的那条 |
| 测试验证 / 验收 / 集成验收 / 观察 | **产出** | 给「执行」的那条 |

这一条是拿实测换来的：只给执行者补一句「别动 src/legacy」→ 执行者照做 → 验收员拿着补话
**之前**定下的验收点对照产出 → 判不通过 → 返工 → 执行者下一轮同时拿到你那句话和「方案
要求改 legacy，未见改动」，两条直接打架 → 撞满 `maxIterations` 阻断。**你自己那句纠正成了
这个节点失败的直接原因**，而屏幕上没有任何东西会让你把这两件事联系起来。

反过来也不多送：给评审的话不会进执行提示词，给分析的话也不会再抄给验收（它已经体现在方案
里，而方案本来就在验收的提示词里）。一条指引在一轮一节点的 24 次调用里被付几遍是实打实的
钱——早先的版本对每个裁决席位都带上分析**和**执行两条，100 节点 × 3 轮多背 11M 字。

每条指引上限 2000 字、点名给角色的最多 20 条，超出会截断／丢弃并**说出来**（关口上那一块）。

#### 失败节点：三个快捷键

光标停在一个**失败**节点上时（树上或详情页里都行）：

| 键 | 做什么 |
|---|---|
| **`R`** | 直接重做**失败的那个环节**——省掉前两屏菜单，直接停在确认屏上 |
| **`s`** | **跳过**失败的那个环节，继续往下走 |
| **`f`** | **强制通过**失败的那个环节——路由和 `s` 完全一样，但**留下一条裁决记录** |

「是哪个环节失败的」不是猜出来的：节点被阻断的那一刻，它正处在哪个状态就记在 `node.md` 的
`failedAt` 里（和 `capCategory` 同一条规矩——记下来，不反推）。所以：

| 失败在 | `R` 会重做 | `s` 跳过之后 |
|--------|-----------|-------------|
| 分析 | 任务重做（重新出方案；有子任务的会先删子树） | **不可用**：跳过它等于让节点带着空方案进评审 |
| 质疑讨论 | 从质疑讨论重做 | 方案照用，直接往下走（0 次评审调用） |
| 执行 | 从执行重做 | **不可用**：跳过它等于承认这个节点什么都没做 |
| 测试验证 | 从执行重做（它跑在执行环节内部） | 不实跑测试，直接进验收（**执行不重跑**） |
| 验收 | 从执行重做（同上） | 不核对验收点，直接评分 → 合并 → 已验收（**执行不重跑**） |
| 集成验收 | 从集成验收重做 | 不裁决「合起来达没达成父目标」，直接判过 |
| 观察 | 从执行 / 集成验收重做（按节点形态） | **不可用**：它不会挡住任何节点，低分只触发一轮返工 |

**跳过测试验证 / 验收时执行环节不重跑**，这是这个键最容易被误解的地方。你要跳过的是
**判决**，不是重做工作——重跑一次执行者不但是这条链上最贵的一次调用，它还会改动代码，
把你刚刚亲自看过、决定放行的那份产出换成另一份没人看过的。所以这两条是从执行循环的
**尾部**进去的。（之后如果验收又不通过而走返工，那一轮**会**真的从执行者开始——那时候
确实需要有人去改代码。）

三种拿不到的情况，都会**说清原因**而不是给一个按不动的屏：

| 情况 | 屏幕上会说 |
|------|-----------|
| 这个节点不是自己失败的 | 「这个节点是因为**它的子任务**失败才停的 —— 请到那个子任务上重做」（`子节点阻断` / `上级任务阻断` / `依赖阻断` 各有自己的一句） |
| 树自己对不上 | 「这棵树自己对不上（依赖成环），不是某个环节失败」 |
| 隔离运行 + 工作区引用已丢 | 不许跳过验收：那会把一个**空工作区**合进集成分支并判「已验收」。请改用「从执行重做」 |

`s` 也有确认屏（一屏），把「跳了哪个环节、之后还跑什么、返工计数清零」摊开，并用 ⚠ 标出
这次跳过**换掉了什么质量保证**。它同样可以按 `e` 补一句提示词——那句话给这个任务的每一个
环节（跳掉的那个环节这次不会发生，往它上面写等于写给一个不存在的读者）。

被跳过的环节在 `node.md` 里记的是「已跳过」而**不是**一条通过记录，而且会写明它是**手工
跳过**的（「用户在阻断后按了跳过」）——一条假的通过记录会让你事后以为有人看过。

#### `f` 强制通过：和跳过的区别只有一条，但那一条是全部理由

圆桌判了不通过、你自己看过产出决定放行——这件事和「跳过」在**路由上逐字相同**（同一个
`planForcePass` 复用了跳过那套重入座位计算：环节照样不开会，执行者照样不重跑，返工计数
照样清零）。差别只在记录：

| | `s` 跳过 | `f` 强制通过 |
|---|---|---|
| `node.md` 的评审 / 验收记录 | **不写** | 多一条 `round`，`PASS`，署名 `人工强制通过` |
| 那条记录的记号 | —— | `MANUAL-PASS`，**不是** `pass`——它和一位真评审员点头必须一眼分得开 |
| 被推翻的那些意见 | 原样留在上一轮里 | 同上，**并且**抄进这条记录的 comments |
| 事后读起来 | 「没人看过」 | 「有人看过并拍板，他放行的是这些」 |

所以选哪个不是口味问题：**没人看过**就按 `s`，**你看过并决定放行**就按 `f`。三个月后翻
`node.md` 的人（可能就是你）只有这一节可读。

能强制通过的和能跳过的是同样那四个环节（质疑讨论 / 测试验证 / 验收 / 集成验收），
不可用时给的原因也逐字相同——包括那条最要紧的：**隔离运行 + 工作区引用已丢时不许强制
通过验收**。跳过它会把一个空工作区合进集成分支并判「已验收」；强制通过在此之上还要记一条
「有人放行过」，严格更坏。

#### 运行中按 `f`：预先批准

`f` 是唯一一个**不必等节点失败**的键。光标停在一个还在跑的节点上按 `f`，会让你从四个环节里
选一个预先批准——「等会儿走到那儿别开会了」。适用的场景很具体：一个节点在返工循环里
反复被同一席挡住，而你已经看过产出决定放行，不想再为下一轮的圆桌付一次钱。

三条要知道的：

- **不打断此刻在飞的调用。** 和「运行中追加指令」同一条规矩——已经开着的那一桌照常开完，
  批准从**下一次**进入该环节起生效。（砍掉在飞的圆桌会把已经判完的席位的裁决变成调用失败，
  那些钱已经花了。）
- **一次性。** 用掉就没了，之后的返工轮照常开会。
- **只活在这次进程里。** 它记在运行控制面上，不写进 `run.md`——中途退出或 `--resume` 之后
  要重按。按 `r` 重做导致编排重开时也会一起失效，届时会明确告诉你失效了几条。

预先批准**不会**让节点跳过执行环节。阻断后按的那次只可能落在一个已经交过东西的节点上，
所以它从判决段进来；而预先批准可以按在一个还没开始干活的节点上——那时候从判决段进来等于
让它一行代码不写就去验收。所以这条路上活照干，只是不开会。

#### 和 `--retry-blocked` 的区别

| | 重做（`r`） | `--retry-blocked` |
|---|---|---|
| 粒度 | 一个节点、一个环节 | 整个运行，所有被阀门挡住的节点 |
| 适用 | 任意节点，**包括已验收通过的** | 只对被安全阀挡住的节点有效 |
| 什么时候用 | 你看了结果不满意，或者知道哪一个节点错了 | run 因为撞上限整体停了，想整轮再来 |

节点连续返工撞满 `caps.maxIterations`（默认 3）被阻断时，`r` → 「从执行重做」是最省的出路：**验收记录保留**（它是返工提示词的反馈来源，清掉等于让执行者从零开始猜），但预算清零。

### 界面：任务树和详情页

**任务树**

| 键 | 做什么 |
|---|---|
| `↑↓` / `jk` | 上下移动 |
| `←` / `→` | 折叠 / 展开子树 |
| 空格 | 折叠状态切换 |
| 回车 | 打开光标那一行的详情页 |
| **鼠标点击** | 和在那一行按回车完全一样：光标移过去 + 打开详情页 |
| `r` | 重做（**运行中也能按**，见下） |
| `R` | **快速重做失败的那个环节**（只对失败节点有意义；运行中也能按） |
| `s` | **跳过失败的那个环节**继续往下走（同上） |
| `f` | **强制通过**：失败节点上是「覆盖那次不通过」，运行中节点上是「预先批准某个环节」 |
| `p` / `i` / `x` | 暂停调度 / 追加一句指令 / 取消光标选中的那个节点（只在运行中有） |
| `+` / `-` | **调并发上限**（只在运行中有；`=` 和 `_` 也认，因为 `+` 要按 shift） |
| `Esc` / `q` | 退出 |

`R` 和 `s` 只在**光标停在一个失败节点上**时才写进底部提示行：它们对一个没失败的节点本来就
不可用，而那一行是截断的——无条件多写 20 列会把右边的「Esc/q 退出」吃掉。

**运行中重做**：一个任务失败了，不用等整棵树跑完再从结束屏重来——当场按 `r` / `R` / `s` 就行，
**别的任务照常跑**。确认之后新树是被**并进正在跑的那一轮**，不是另起一个编排器（另起一个的
后果是同一批节点被派两遍，而老编排器还攥着它们在飞的调用）。两道闸门顶着：

- 目标节点**自己正在跑**时不许重做，屏幕会让你先按 `x` 取消它——替你砍掉一个在飞的调用
  不是这个键该做的决定；
- 落盘**之前**先把这次重做要动的节点（目标 + 被删的子树 + 被放回的祖先 + 被改写依赖的）
  从调度里扣下来，换完树再放。少了这一步，算新树和落盘之间那次 `await` 里调度器完全可能
  把其中一个派出去——最真实的是被放回的祖先，别的子任务恰好这时跑完，它就进了集成验收。

编排器已经收尾的那一瞬按下的重做会退回结束屏那条路（重启一个编排器），而不是悄悄改一棵
没人再调度的树。

`f` 的提示**跟着光标所在节点的状态换措辞**（失败节点上写「强制通过它」，运行中节点上写
「预先批准」）：这个键在两种节点上做的是两件事，写死一句的话总有一半时候那一行在说另一件事。

**并发上限的键写在表头**（`并行 2/7 +/-`），不在底部提示行：运行中那一行实测已经 123 列，
在 80 列终端上右半截整个看不见，而这个键要改的那个数字就在表头。窄于 72 列时那三个字符
不画——4 列换一个折成两行的表头不值，而表头一折行，底部的图例和按键提示就被顶出屏幕。

#### 运行中调并发度

`+` / `-` 一次一步，范围 1–64。语义是**「先别派新的」，不是「把正在干的活炸掉」**：

- **调高**：还没起跑的节点**立刻**起跑，不等在飞的那个跑完。（等的话，一个二十分钟的执行
  环节就是二十分钟的「按了没反应」——而那正是你去调它的时刻。）
- **调低**：在飞的调用一个都不受影响，全部照跑完；只影响接下来还能不能派新的。所以表头会
  短暂显示 `并行 5/2`（5 个在跑、上限 2）——那是**实话**。
- **下限是 1**，不是 0：0 的语义会让调度器把「用户调小了」误判成「树走不动了」并以
  `blocked` 收尾。想暂停请按 `p`，那条路是可逆的。
- **评审团也跟着走**。上限约束的是同一个全局池，所以一个 5 席评审团在调低之后不会继续按
  旧上限并发——那正是把调用数乘起来的地方。
- 新的数字会写进 `run.md`，所以 `--resume` 接着用它，事后也查得到这一趟到底按几并发跑的。

按住 `+` 被终端合批成 `+++++` 时**只走一步**（和 `jk` 那条「按住多久滚多远」的规矩不同，
是故意的）：这个数字每一步都会真的多派一个带写工具的执行者出去。

**鼠标点击要终端在报告点击才有用**，而这需要全屏模式（`CLAUDE_CODE_NO_FLICKER=1`）——
非全屏时终端根本不发这些序列。所以任务树页脚只在真的能点时才写「回车/点击看详情」：
那一行是截断的，多塞一句「需要开全屏」会把右边的「Esc/q 退出」吃掉。
「为什么点不了」写在详情页页签条的右边；窄终端上那里也放不下整句时会退化成 `鼠标✗`。

**详情页**分成两个页卡，页签条在最下面：

- **任务**：目标 / 完整方案 / 重点 / 风险点 / 验收点 / 执行状态 / **补充指引（你写的）** / 依赖 / 阻断原因 / 评分 / 迭代次数 / 各阶段耗时 / **模型用量** / 评审记录 / 验收记录 / 隔离工作区
- **子 agent 输出**：每次模型调用一条流，带署名（哪个环节、第几轮、哪个员工、什么模型）

| 键 | 做什么 |
|---|---|
| `←` / `→` | 换页卡 |
| **鼠标点击页签** | 换到那个页卡 |
| `Tab` | 焦点在「页签条」和「内容区」之间切；焦点在页签条上时回车/空格进入内容 |
| `↑↓` / `jk` | **两个页卡同一条规矩**：折叠着的那一项选段落 / 选阶段，展开着的滚它的内容 |
| 空格 | 展开/收起选中的那一段（任务页卡）或那条流（输出页卡）——展开之后 `↑↓` 就归内容 |
| `^u` / `^d` | 任务页卡翻页 |
| `g` / `G` | 输出页卡到顶 / 到底（到底会恢复跟随最新） |
| `n` | 下一项：任务页卡换一段，输出页卡换一条流。**两种模式下都认** —— 读到一半想换不必先收起 |
| `t` | 输出页卡展开选中那条流的思考原文（默认折叠成段数——思考会把工具调用淹掉） |
| `Esc` / `q` | 返回任务树。**任何时候都能返回**，没有死角 |
| `r` | 重做本任务（run 结束后才有） |
| `R` / `s` | 重做 / 跳过失败的那个环节（只对失败节点写出来） |

**输出页卡的 `↑↓` 有两个含义，由选中那条流折没折决定：**

- 选中的流**折叠着** → `↑↓` 在各阶段之间走（它折着，本来也没有内容可滚）
- 选中的流**展开着** → `↑↓` 滚它的内容

空格正好是切换折叠的键，所以「选阶段 → 空格展开 → 上下读 → 空格收起 → 再选下一个」是一条
顺手的路。

**打开时选中的是最后一条流**，也就是最新那一次调用——一个节点还在跑的时候那就是正在跑的
那条，而它默认展开，所以进去 `↑↓` 直接滚它的实时输出，和以前一样。（选第一条的话就不是了：
一个在跑的节点手上必然已经有几条收口的分析／评审流，它们默认折叠，`↑↓` 会变成选阶段——
而你进来是为了看那条正在跑的输出。）跑完的节点最后一条也是折叠的，`↑↓` 自然回到选阶段。

底部提示行会跟着这两种模式换文案（写死一句「滚动」的话，在折叠态下按 `↑↓` 换的是流，
而提示行说它在滚动）。

`↑↓` 之外的键**两种模式下完全一样**：滚轮、`PgUp`/`PgDn`、`^u`/`^d`、`g`/`G` 一律是滚动。
一格滚轮是 3 行，当成「往下跳 3 条流」的话轻轻一拨就飞过整个列表。

**详情页只在全屏模式下真的满屏。** 全屏时它渲染在 Claude Code 的模态槽里，可用行数是
`终端行数 - 3`，能吃满。非全屏时它**刻意留 8 行余量**给上面的对话——占满会让每秒一次的
耗时刷新逼出整屏重绘，而且被切掉的是顶部（标题和目标），和全屏正好相反。

终端窄到排不出可读内容时（内容区不足 20 列），详情页会直接说「终端太窄」，而不是硬排——
硬排的后果是行回流、最后一行被静默剪掉，而画面的总行数一点没变。

**模型写的那几段按 markdown 上色**：目标 / 完整方案 / 重点 / 风险点 / 验收点 / 执行状态 / 评审记录 / 验收记录。

标题、加粗、行内代码、列表、引用走的是主 REPL 那一套（复用的就是那份 `formatToken`）。

**有两处不一样，先说清楚，免得这句话自己变成假话**：主对话流把表格交给 `MarkdownTable`
这个 React 组件（按终端宽度分列宽、格内折行、太高转竖排），代码块还带语法高亮；而详情页
是按行出字符串的，用不上组件，也不做异步的语法高亮。所以这儿的**表格排得下才用对齐版、
排不下退回你写的原文**（对齐版不看窗口宽度，硬排会撑到一百多列、续行还丢掉行首的 `|`），
**代码块**保留围栏并把围栏压暗，正文不上色。

**任务清单**（`- [x]` / `- [ ]`）保留勾选标记 —— `formatToken` 会把它整个剥掉，
于是「已完成」和「未完成」长得一模一样。

**折叠预览里不留空行**：一段只给 3~6 行时，空行就是一半的篇幅。展开之后照留。

**机器生成的那几段一个记号都不动**：依赖 / 阻断原因 / 评分 / 迭代次数 / 时间 / 各阶段耗时与时间点 / 模型用量 / 隔离工作区。

它们里面是 id、路径、`--flag`、`[WAITING_CHILDREN]`——交给 markdown 解析器只会被吃掉记号。
阻断原因还额外有一层语义红色，那层颜色不能被顶掉。

终端不支持颜色时（`chalk.level === 0`，比如管道重定向）**整个不上色，原文原样出**——
剥掉 `##` 和 `**` 又不上色是纯粹的信息损失。

### 模型用量：每个任务花了多少

详情页的「模型用量」一段回答两个问题，有子任务时给两行：

```
本节点: 4 次调用 · 11.0k tokens · 输入 10.0k / 输出 1.0k
含 3 个子任务（整棵子树）合计: 27 次调用 · 214.5k tokens · 输入 60.0k / 输出 9.5k · 缓存 读 143.0k / 写 2.0k
```

- **一次调用 = 上游的一次请求**，不是「一个环节」也不是「一个席位」：一席在工具循环里
  跑十轮就是十次调用，那十轮的钱是真花了的。去重按 `request-id`（第三方网关不给这个头，
  所以翻译层给自己的每一次响应都签一个），拿不到时才退回消息 id。
- **子树合计是读的时候现算的**，不落盘。存合计的话，一个节点的用量变化要同时改它到根的
  每一个祖先，而这条链上任何一次崩溃或重做都会让那些数字永久对不上，却没有任何东西会报错。
- **缓存读写单列**。它在计费上便宜一个数量级，但总量那一格是**全量**——一个高度复用
  上下文的运行，缓存读常常就是大头，漏掉它这个数字等于没有。OpenAI 两条协议上，
  `cached_tokens` 会从「输入」里减出来单列，口径和 anthropic 协议一致。
- **重做不清零**。钱花掉了就是花掉了 —— 任务重做会删掉整棵子树，那部分的账**记在重做目标身上**
  （详情页多一行「已废弃(重做删掉的子任务)」），所以表头那个总数不会因为一次重做而倒退。

任务树上也有：每一行末尾的 `⇅12/34.5k` 是**含子任务**的合计（折叠着的拆分节点，人想
知道的正是「这一整块花了多少」），表头的 `⇅120 次 · 1.2M tokens` 是整趟的合计。
窄终端上行里那个标记会**整个让位给标题**——树行回答的第一个问题永远是「这是哪个任务」。

**`≈` 表示这个数是估出来的。** 两种情况拿不到真实用量，而它们**都不是我们能改的**：

- **OpenAI 兼容网关忽略 `stream_options.include_usage`**（实测存在）。我们发了，它不认，
  那一次调用的真数就永远拿不到。
- **CLI 档员工**：它是另一个进程，除非它自己在协议的 `result` 行里报 `usage`，外面只看得见文本。

这两档会按「请求体 + 产出正文」估一个数（拉丁约 4 字符 1 token、中日韩约 1.5 字符 1 token，
思考和工具参数都算进产出），并在界面上带 `≈`，详情页还会写明「其中 N 次是估算」。
**上游只报一半时**（只给 `prompt_tokens`、`completion_tokens` 是 0）也走这一档：给了的那一侧
原样留着，缺的那一侧才估，整条仍然标 `≈` —— 一半真一半假而不标记，比全 0 更难被发现。

CLI 档的估算只覆盖**我们发过去的提示词和它交回来的最终答案**：那个子进程内部的系统提示词、
几十轮工具循环，外面一概看不见（方向是低估）。想要准数，让那个 CLI 在协议的 `result` 行里
带上 `usage`。同理，`apiProtocol: "anthropic"` 那一档是**原样转发**、不解析流，所以网关把
usage 报成 0 时我们估不出来（那一档只补 `request-id`，好让自动压缩的账仍然记得到人头上）。
**误差方向不保证，别拿它当计费依据**——但一个标着 `≈` 的粗略数字是实话，而原来那个 0
是假话：那些 token 是真花掉的，而 0 会让整段用量在界面上消失（用户报的「统计没了」就是这个）。

**还剩下什么漏算**：

- 启动关口那次一次性的配置提取调用（1 次，量级可忽略）。
- 根方案起草失败时，那一趟的账随被丢弃的 root 对象一起没了。

**子 agent 里的自动压缩已经算进来了**（它以前是最大的一个洞：一次压缩就是一次读满上下文
窗口的完整调用，而产出以 `UserMessage` 回到主循环，消息那条路一条都看不见）。现在每一次
真实请求在 `claude.ts` 结算成本的同一处旁路上报一份，按 `request-id` 和消息那侧去重。

子 agent 自己再开 Task 也不走这条路，不过默认配置下 `ALL_AGENT_DISALLOWED_TOOLS` 把 Task 挡在
子 agent 之外，所以它发生不了。provider 报错那种合成消息也不算一次调用——算进去的话「调用次数」
会随着报错次数虚涨，而那正是你想拿它判断的东西。

### 子 agent 输出里能看到什么

每一次模型调用一条流，里面按到达顺序是：模型说的话、它调了什么工具（含 `mcp__*`，
显示成 `<服务器> - <工具名> (MCP)(参数)`）、工具返回了什么、报没报错、以及**这次调用花了多久**。

```
▾ 方案 第1轮 · 架构师 (deepseek-reasoner)              ◐ 运行中 · 2 工具 · 12s
│ ✻ 思考 3 段（t 展开）
│ 我查一下仓库里未关闭的 issue。
│ ● gitlab - List Issues (MCP)(acme/web)
│ ● ctx7 - resolve-library-id (MCP)(react-router)
│   ⎿ gitlab - List Issues (MCP)(acme/web) · 1.8s · #412 登录页 500
│   ⎿ ctx7 - resolve-library-id (MCP)(react-router) · 900ms · MCP error -32001
```

**跑完的流默认是折叠的**（`▸`），只留一行「最新: …」——一次运行会开几十条流，全铺开就没法看了。
折叠那一行同样带归属和耗时：`▸ 方案 第1轮 · 架构师  ● 已完成 · 2 工具 · 12s` /
`│ 最新: ⎿ Bash(bun test) · 1.8s · 2043 pass`。按空格展开选中的那条。

页签上的 `(N 次调用)` 是**这个节点开过几次模型调用**（一次调用一条流），不是 agent 数；
上限 40 条，超了会把最旧的已收口流压成「只留表头和最后几条」。

并行调用时返回是错序到的，所以每条 `⎿` 会写清自己属于哪一次调用；紧跟在自己调用行
下面时就省掉不写。耗时量的是「调用发出到返回」的墙钟——**包含等你批准工具权限的时间**，
和主 REPL 一个口径。这句口径在输出页卡的页脚上也写着，免得一个等了十分钟批准的
`Bash` 被读成「这个测试跑了十分钟」。

**模型说的话也按 markdown 上色**（思考正文同样，而且仍然是暗的——少了那层暗色就分不清
哪句是想的、哪句是说的）。**工具调用行和工具返回行不上色**：里面全是路径、`--flag`、
`[TAG]`，解析一遍只会被改写。**代码围栏（```）里也不上色**，围栏行本身照原样画出来——
删掉它人就分不清代码从哪开始。

**OpenAI 协议的员工也能看到思考。** 兼容后端把推理放在 `reasoning_content`
（DeepSeek / Kimi / GLM / 通义 / MiniMax / vLLM）或 `reasoning`（OpenRouter 等）字段上，
这些默认就有，不需要配 `thinkingDepth`；`thinkingDepth` 在这条协议上译成 `reasoning_effort`，
只对「把推理藏在这个参数后面」的网关有意义。OpenAI 自家的 `chat/completions`
**不暴露推理正文**，所以真 OpenAI 后端在这条协议上没有思考可显示。

**要看真 OpenAI 的思考，用 `apiProtocol: "openai-responses"`。** Responses API
（`{apiUrl}/responses`）会给出推理摘要，这条桥把它渲染成思考内容。它还要求带工具调用的
轮次把上一轮的推理片段一起回传，否则上游 400——这件事由桥自己处理（`store: false` +
`include: ['reasoning.encrypted_content']`，密文搭 thinking 块的签名往返），你不用配任何东西。

**三种协议收得下的思考档位不一样**，写不进去的会被翻译，而且会在 `/et` 启动关口上说出来：
`xhigh` 两边协议都收；`max` 是 Anthropic 独有的，在 OpenAI 两条协议上译成 `xhigh`；整数只有
anthropic 收。Anthropic 协议下模型不支持 effort 参数时（比如 `claude-3-5-sonnet-20241022`），
这个值**整段不发**——关口上会写明。详见 `docs/roles-setup.md`。

**员工配置写错时不再一言不发。** 协议名少写一个字母、`thinkingDepth` 写成认不出来的值，
以前的表现是「这个员工不存在」而屏幕上零提示（`console.error` 被 ink 的 `patchConsole`
吞进 debug 日志了）。现在这些原因会出现在 `/et` 启动关口的「你的请求中有以下部分不会生效」
那一块里。

## 子 agent 继承什么：MCP 与 CLAUDE.md

项目里配了 `.mcp.json` 和 `CLAUDE.md`，主模型会加载。子 agent 呢？

**一句话：同进程的子 agent 全继承；另起进程的（`execMode: "cli"` 的员工）一样都不继承。**

| 子 agent 形态 | MCP 工具 | CLAUDE.md |
|---|---|---|
| 普通子 agent，没写 `tools` 或写 `["*"]` | 继承 | 继承 |
| 普通子 agent，写了显式 `tools` 白名单 | 继承 | 继承 |
| 内建 `Explore` / `Plan` | 继承 | **不给** |
| `/et` 的七个环节 | 继承 | 继承 |
| `execMode: "api"` + anthropic 协议 | 继承 | 继承 |
| `execMode: "api"` + openai / openai-responses 协议 | 继承 | 继承 |
| `execMode: "cli"` | **不继承** | **不继承** |

**协议那一轴整个不影响，原因值得单说**：CLAUDE.md 不走 system prompt，它被拼成**一条领头的 user 消息**（裹在 `<system-reminder>` 里）。user 消息在三种协议上都有对等物——`chat/completions` 映成 `{"role":"user"}`，Responses 走同一条消息列表（`instructions` 只接 system，而它本来就不在那儿）。所以换协议丢不掉它。

顺带一条容易踩空的：**`AGENTS.md` 不是自动加载的指令文件**，`.cursorrules`、`.github/copilot-instructions.md`、`.clinerules` 也不是。它们只被 `/init` 读一次、把内容抄进 `CLAUDE.md`。真正会自动加载的只有 `CLAUDE.md`、`.claude/CLAUDE.md`、`CLAUDE.local.md`、`~/.claude/CLAUDE.md` 和 `.claude/rules/*.md`——项目规范要生效就写这几个，而且**主模型和子 agent 是同一份**，不存在「主模型读到了、子 agent 漏了」。

### 四个例外

- **`Explore` 和 `Plan` 拿不到 CLAUDE.md。** 只有这两个内建员工带 `omitClaudeMd`，理由是「只读 agent 不需要 commit/PR/lint 规则」。后果：CLAUDE.md 里「搜索时排除 vendor/」这类**指导探索行为**的规范，对这两个是白写的。
- **显式 `tools` 白名单管不到 MCP —— `mcp__*` 无条件继承。** 白名单本身仍是精确全名匹配（内建工具确实要一个个写全），但 `mcp__*` 在白名单之外被无条件补回来，所以 `tools: ["Read", "Grep"]` 的 agent 照样拿得到项目 `.mcp.json` 里的全部工具。不写 `tools` 或写 `["*"]` 才是全给。要收回某个 MCP 工具只能用 `disallowedTools`。
  （**这条 2026-08 改过。** 此前白名单是纯查表，任何一个写了 `tools` 的 agent 都会被静默拿掉全部 MCP——配置里一个字没提 MCP，表现却是「主模型能用、子 agent 用不了」，而且没有任何报错。）
- **改完 CLAUDE.md 要重启。** 它在进程里只读一次并缓存，会话中途改完，**后面新起的子 agent 拿到的仍是启动时那份快照**。
- **子目录的 CLAUDE.md 走另一条路。** 它不在上面那条消息里，是读到该目录下的文件时才注入的，而且每个子 agent 有自己独立的去重表——父 agent 已经加载过，不会把子 agent 的那份顶掉。

### 怎么确认它真的加载了

MCP 只在**会话启动时由主进程连一次**，之后没有「某个子 agent 去加载 MCP」这件事——它继承的是同一份工具表。所以没有一条「子 agent 正在加载 mcp.json」的日志可看，能看的是这三处：

| 看哪 | 说明什么 |
|---|---|
| `/mcp` | 服务器连没连上。这是最上游的一处：没连上，后面全都是空的 |
| `/et` 启动关口的 `MCP 工具:` 那一块 | 本次会话的 `mcp__*` 工具名 **+ 每个服务器的连接状态**。这块整个不出现＝会话里一个 MCP 工具都没有，子 agent 当然也没有 |
| 子 agent 日志窗口的**第一行** | 每次派发都打头一行 `[工具 23 个 · 其中 MCP 5 个：gitlab、ctx7]`。没有 MCP 时写 `[工具 23 个 · 无 MCP]` |

最后那一行是专门为这个问题加的：工具表退化成空的，在窗口里和「模型自己不想调工具」长得一模一样，此前没有任何一处能把两者分开。

**关口那块显示为空、但你确实配了 `.mcp.json`**，九成是项目级服务器卡在**待审批**——待审批的服务器不连接，于是它一个工具都不贡献。预批：

```jsonc
// .claude/settings.json
{ "enabledMcpjsonServers": ["gitlab", "ctx7"] }   // 或 "enableAllProjectMcpServers": true
```

想重新弹审批框：`claude mcp reset-project-choices`。

### `execMode: "cli"` 的员工怎么让它们生效

cli 员工是**另一个进程**，父进程只递给它一样东西：提示词。所以没有「继承」开关，只有三条路。先看清它实际拿到什么：

| | |
|---|---|
| 继承 | 环境变量；工作目录（`cwd` 不填就是父进程的） |
| 只收到 | 提示词。默认档整段写进 stdin 然后关闭 stdin，**stdout 整个当结果** |
| 收不到 | 工具表、MCP 连接、CLAUDE.md 那条消息 |
| 也收不到 | **员工自己配的 `prompt`（系统提示）**——这条最容易踩，它算出来了，但只喂给 api 档 |

#### 路一：让子 CLI 自己去发现（`command` 就是 `claude` 时最省事）

**CLAUDE.md 默认就通。** `cwd` 不填就继承父进程的工作目录，通常正是项目根，子 claude 自己走目录发现就读到了。只有把 `cwd` 指到项目外才会断。

**`.mcp.json` 默认不通，这条得动手。** 子进程是非交互的，弹不出审批框，项目级 MCP 服务器会停在「待审批」而不连接。预批一下：

```jsonc
{ "enabledMcpjsonServers": ["gitlab", "ctx7"] }   // 或 "enableAllProjectMcpServers": true
```

#### 路二：用 `args` 显式喂

```jsonc
{
  "name": "cli-评审",
  "whenToUse": "独立评审",
  "execMode": "cli",
  "command": "claude",
  "args": [
    "-p",
    "--add-dir", "/abs/path/to/repo",
    "--mcp-config", "/abs/path/to/repo/.mcp.json",
    "--settings", "/abs/path/to/repo/.claude/settings.json",
    "--append-system-prompt-file", "/abs/path/to/repo/CLAUDE.md"
  ]
}
```

三点：`-p` 是**必须的**（父进程的协议就是提示词进 stdin、stdout 整个当结果，不是 print 模式会挂在那儿等交互）；`--append-system-prompt-file` 是把上面那条「员工 `prompt` 被丢掉」补回来的唯一办法；`args` 是**原样数组、不过 shell**，所以 `"--add-dir /path"` 合成一个元素是错的，`~` 也不会展开，写绝对路径。

#### 路三：包一层 wrapper —— 要设环境变量只有这条

`roles[]` 是严格校验的，**而且没有 `env` 字段**。后果比「该字段不生效」严重：多一个未声明的键会让**整条员工被跳过**（表现成「这个员工不存在」）。所以别试着加 `"env"`，用脚本：

```bash
#!/usr/bin/env bash
# scripts/role-reviewer.sh
cd /abs/path/to/repo || exit 1
export ANTHROPIC_BASE_URL=...
export ANTHROPIC_API_KEY=...
exec claude -p --add-dir . --mcp-config .mcp.json
```

然后 `"command": "scripts/role-reviewer.sh"`、`args` 留空。wrapper 顺手把工作目录和那串长旗标也解决了——配置文件里只留一个路径，调什么都在脚本里改。**推荐这条。**

#### 子 CLI 不是 `claude` 时

codex / gemini / 自研程序认不认 `CLAUDE.md` 完全是它自己的事（`AGENTS.md` 这套约定就是这么冒出来的）。这时别指望文件发现，把规范**拼进提示词**才可靠：wrapper 里 `cat CLAUDE.md` 前置，或者用它自己的 system-prompt 旗标。

> **`interactive: true` 不是「要不要界面」。** 它是说「这个程序实现了那套双向 JSON-lines 协议」——父进程发 `{"type":"task","prompt":…}`，子进程回 `{"type":"permission_request",…}` / `{"type":"result","content":…}`，每行一个 JSON。普通 `claude -p` **不说这套协议**，给它配 `interactive: true` 会卡住。不确定就别写：默认的单次档适用于任何「吃 stdin、吐 stdout」的程序。

> **`/et` 派发不了 cli 员工。** 它们会在启动关口被剔除并说明原因，而不是静默降级成主模型。所以如果目标是让 `/et` 的环节用上，正解不是把 cli 配通，是改成 `execMode: "api"`——那条路上 MCP 和 CLAUDE.md 都自动继承，两种协议都一样。

## 自行编译

```bash
bun install

# 打包成单个 JS（需要目标机器有 bun）
bun run build            # → dist/cli.js

# 编译成单文件二进制（目标机器什么都不需要）
bun run build:compile    # → dist/claude-haha

# 交叉编译
bun run scripts/build.ts --compile --target bun-windows-x64 --outfile claude.exe
```

版本号来自构建时的环境变量，不注入则是 `999.0.0-local`：

```bash
CLAUDE_CODE_LOCAL_VERSION=v0.1.0 bun run build:compile
```

### 关于 `vendor/zod-v4.js`

仓库里提交了一份**压平后的 zod**。原因：bun 1.3.14 给 zod 的 `export *` 链生成的懒导出表会引用不存在的符号，主构建产物一跑就 `ReferenceError: _uppercase2 is not defined`（不是重复打包——产物里只有一份，而且单独打包 zod 完全正常）。先把它压平成一个文件、主构建再指向那一份，就绕开了出问题的那条 codegen 路径。

升级 zod 之后重新生成：

```bash
bun run vendor:zod
```
