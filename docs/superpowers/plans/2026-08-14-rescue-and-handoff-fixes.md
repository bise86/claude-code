## 要改的

### A. 完成判据:合到主干才算完(用户总纲)
1. **`m` 键收尾复核**。`efftask.tsx:2643` 清 `pendingHandoff` 的判据是
   `trunk.ok === true && heldBack === 0`,而 `heldBack` 只数 hold / failed / stranded ——
   **从不回头验一遍「这些 ref 现在是不是真的都是 HEAD 的祖先」**。加逐条
   `merge-base --is-ancestor <ref> HEAD` 的收尾复核,不全通过就不许说完成。
2. **`undeliveredCommits` 要把 salvage / 节点分支算进去**(`startupConfirm.ts`)。
   只看 `commits` 就是 .13 那种「0 待合 + 44k 失联」照样报完成。
3. **捞回要进自动收口**:`scanStranded` 全仓库只有 `m` 一个消费者
   (`mergeSubtree.ts:473`),而 `m` 只能手按。`finishHandoff` 合主干**之前**跑一次全量。

### B. `handoff()` 的两条噪音判据(`worktreePool.ts`)
4. `:1256` 的 salvage 是一句裸 `for-each-ref`,**不判合没合入**;而 `rescue.ts:405`
   写死「成功不删分支」。两条加起来 = 抢救分支永久出现在每一次收口屏上,
   而底下那行「⚠ …不在集成分支上」在合过之后是假话。
   对照 `stranded.ts:469` 判得是对的(`containedIn === 'yes' → continue`)。
5. `:1271` 的 `kept` 用 `status --porcelain --ignored`,于是**构建产物被算成
   「仍有未合入的内容」**。判据换成「真有未合入的提交或已跟踪改动」。

### C. 冲突解决:两半都可能是对的(用户点名)
6. **add/add 且两侧是同一源文件的不同区间时,不许二选一,必须并集。**
   现场实证:`pkg/sql/sem/tree/eval.rs` 两侧分别是 eval.go 的「前段」和
   「3669..6516 行」,master 侧 100 个顶层定义、integration 侧 105 个,取任一边丢一半。
   `autoResolveMerge` 现在只把冲突文件丢给模型,提示词里**没有一句**说这种可能。
   要给解冲突提示词加这条判据,并且:**顶层符号撞名必须报错停下,不许自动挑一个**
   (现场那 11 个撞名里,master 侧逐个都带 `TODO: replace with real declaration`,
   是可判的;但"可判"要由证据得出,不是默认取一边)。

### D. 构建产物:根治在事前,补救在 `c` 键(用户:「删除产物可以放到 c 键啊」)
7. **事前**:`worktreePool.init()` 已经在往 `.git/info/exclude` 写
   `.claude/efftask/` 和 `.efftask-worktrees/`,把 cargo/构建产物目录一并写进去 ——
   2 681 个文件的真正来源是执行者自建 target 目录 + `commitAndMerge` 的 `add -A`。
8. **补救**:`c` 键(`buildOutputs.ts` / `cleanupWorktrees.ts`)现在只清**被忽略的**
   (`clean -X`),对**已被跟踪**的一个都碰不到,恰好漏掉本次这一整类。加一格
   「这些产物已经被提交进版本库了:取消跟踪并删除」。
   **判据按签名,不按名字**:cargo 在每个 target 目录放 `CACHEDIR.TAG`,首行
   `Signature: 8a477f597d28d172789f06886806bc55`。实测覆盖 master 115 个目录 / 2 383 个文件。
   剩下靠名字命中的进**第二桶,默认不选**;两桶里出现源码扩展名就**整桶拒绝**。
   `git check-ignore` 判覆盖率时**必须带 `--no-index`** —— 默认它查索引,
   已跟踪的文件一律报「未忽略」,不带这个开关那道自检恒真、什么都证明不了(现场踩过)。

### F. 「没合并成功就标注任务成功」(用户点名,已量出确切数字)

**实测(.30 run 001,抢救前的状态)**:74 条抢救分支**没有一条**在集成分支里;
按提交信息认回主之后,其中 **67 条的属主节点 `status: ACCEPTED`**,7 条认不回主。
全 run 1009 ACCEPTED / 14 BLOCKED。

也就是说:**67 个被判通过的任务,产出躺在一条没进集成分支的 ref 上**,更别说主干。
而这一趟从头到尾报「完成」。

10. **捞回**不该**改节点状态。** `mergeSubtree.ts` 顶上那条规矩是对的
    ——「合并是 git 上的事,不是『这个任务通过了』」。把捞回来的废稿标成 ACCEPTED,
    等于签发一份从来没发生过的判决(和第十六轮 `nodeRepair` 那条同源)。
11. **该补的是「投递事实」这一层,它不是判决。** 按 `reworkReason` 那个路子做:
    **派生,不新增落盘字段**(一次性标记这个仓库付过三次学费)——
    `deliveredTo(node)` = 这个节点的产出在不在集成分支/主干上,由 git 现算。
    - **集成验收看得到它**:产出不在集成分支上的节点不该通过集成验收;
    - **树上显示它**:ACCEPTED 但未投递要看得见,而不是和真投递了的长得一模一样;
    - **run 的完成判据用它**(= A.2):任何一条还没投递就不许说完成。
12. **捞回之后变的是投递事实,不是状态** —— 状态原样,`deliveredTo` 由假转真,
    于是 A.2 那条完成判据自然被满足。这样「捞回」和「判决」各归各的,两边都不说谎。

### G. 「零贡献」这条链上真正坏掉的两处(先纠正一次我自己的误判)

**误判记录(留着,因为它是本轮第三次同类错误):** 我先用
`grep -c contributed src/tools/efftask/persistence.ts` = 0 断定「从不落盘」。
那个探针什么都证明不了 —— `serializeNode` 是 `const fm = { ...node }` + `yamlStringify(fm)`,
**整个节点对象都落盘**。跑机实测:1023 个 node.md 里 **829 个带 `contributed: true`**。
同一轮里另外两次同类:`git check-ignore` 少了 `--no-index`(已跟踪文件恒报未忽略)、
改注记时在替换文本里**引用了判据要匹配的那个串**(改完照样命中)。
教训统一成一句:**探针必须能区分「真的没有」和「我没查对地方」。**

**重新分类**(.30,执行型终态节点 851 个):

| | 数量 | 含义 |
|---|---|---|
| ① `contributed: true` + 有注记 | 14 | 交付过,只是后来某轮没新产出 —— **不是丢** |
| ② `contributed: true` 无注记 | 645 | 正常交付 |
| ③ 无 `contributed` + 有注记 | **185**(181 ACCEPTED / 4 BLOCKED) | **从没交付过**;其中编译验证类 129、**真活 56** |
| ④ 无 `contributed` 无注记 | 7 | 会被 `resumeCore` 静默回填成 `true` |

③ 不是闸失效:跑机二进制**带**那道闸(`grep -a no-output/NO_CONTRIBUTION/outputMissing` 都命中),
但它 2026-08-14 11:39 才部署,而这 181 个是同一趟 run 更早的阶段由老二进制处理的。

**真正的活 bug 有三处,都很小:**

13. **`pipeline.ts` 的注记是无条件追加的** —— `!res.merged` 就写
    「该节点没有向集成分支贡献任何改动」,而 `contributed === true` 的节点**交付过**,
    这句话在盘上是假的(① 那 14 个)。按 `contributed` 分两句写:
    交付过的写「本轮没有新的改动可合并」。
14. **`backtrack.outputMissing` 只认注记、不看 `contributed`** —— 于是 ① 那 14 个会被 `b`
    点中白重跑。判据补 `n.contributed !== true`。13 和 14 互相喂:假话进盘,而唯一的读者只认这句话。
15. **`resumeCore` 那条回填分不清「老 run」和「这一趟里没走过合并的节点」** ——
    判据是「ACCEPTED 且没有注记 ⇒ 当初合成功过」,对 ④ 那 7 个不成立(它们**从没走过**
    `mergeAndRelease`,既没有字段也没有注记)。改成**run 级**判据:这一趟里只要有**任何**
    一个节点带 `contributed` 字段,就说明这份盘认得这个字段 → 不回填;一个都没有才是真老 run。

### H. 现场实测:哪些任务判了成功、实际没有代码合入(用户点名要的那份清单)

`kind` 只分 executable/decompose,没有「验证型」这一档)。
